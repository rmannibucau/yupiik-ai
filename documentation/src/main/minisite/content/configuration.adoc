Configuration is resolved from, highest priority first:

. CLI arguments: `--yca-<key> <value>` (for example `--yca-provider-model`). The
  `yca.` prefix may be omitted, so `--provider-model` works too.
. JSON file: `~/.yupiik/coding-agent/configuration.json` (override the location
  with the `yca.configuration.json` key)
. System properties: `yca.provider.model` style keys
. Environment variables: `YCA_PROVIDER_MODEL` style keys (dots/hyphens become
  underscores, uppercased)

The `provider` group (`yca.provider.*`) supports multiple providers. Each entry
has an `id` referenced as `$<id>/<model>` anywhere a model is expected (main
model, `model.compact`, code graph enrichment).
`yca.provider.defaultProvider` selects the active entry (blank falls back to the
first, then to the implicit `default` provider). A provider's optional
`providerSpecificOptions` JSON object is merged into every API call payload for
it (eg. `{"reasoning_effort":"high"}` for OpenAI, or an Anthropic extended-thinking
shape such as `{"thinking":{"type":"adaptive","display":"summarized"},"output_config":{"effort":"max"}}`
on an Anthropic-compatible gateway like Azure AI Gateway; an explicitly configured
reasoning shape fully overrides the implicit/variant-derived one). For
single-provider setups, the flat `yca.provider.*` scalars build the
 implicit `default` provider.

TIP: how yca shapes the request payload per provider/model - reasoning effort,
output budget, variants and the opencode parity reference - is documented in
<<features/provider-tuning.adoc,Provider tuning>>.

Each provider can also declare `backgroundModelOverrides` (same
`compact`/`prune`/`memory` shape as `yca.model`) to override the global
background models for the sessions running on it. Resolution per field:

- a non-blank, non-`inherit` value is that model: a bare name is the
  provider's own model (implicitly routed to this provider, even when it is
  not listed in `models`), a `$provider/model` reference keeps its explicit
  routing (eg. a small local provider borrowing a remote summarizer);
- the `inherit` keyword resolves the global `yca.model.*` chain instead
  (including its `memory` -> `compact` and `prune` -> `compact` fallbacks);
- a blank value (the default) means the provider's own default model, ie. no
  dedicated background model for this provider.

A provider-level entry wins over the global one field by field, so a provider
can override `compact` while `inherit`ing `memory`. Code graph enrichment
(`yca.structural-code-graph.model`) keeps its own explicit override; when unset
it follows the default provider's `backgroundModelOverrides.compact`, then the
global chain.

A provider's `dynamicHeaders` are handlebars templates rendered into every
request to that provider (chat, streaming and models). They are resolved in
core (the llm client stays vendor-agnostic: it receives a per-request header
customizer from the caller). Each template is compiled once per provider and
re-rendered per request; a rendered blank value is skipped and a dynamic header
wins over the static `headers` map and over the default API-key authorization
when it targets the same name. The `exec` helper runs a command and returns (by
default stripped) stdout:

[source,json]
----
{
  "provider": {
    "dynamicHeaders": {
      "authorization": "Bearer {{exec \"exec_options=ttl=3600,strip=true\" \"MY_ENV=foo\" \"MY_OTHER_ENV=bar\" \"somebin\" \"somearg\" \"someotherarg\"}}"
    }
  }
}
----

`KEY=VALUE` leading arguments are child environment entries, `exec_options` is
a comma-separated `key=value` list (`ttl=N` caches the stdout for N seconds
across renders and providers, `strip=true|false` trims the output, `strip`
defaults to `true`), and every remaining argument is the command line (command
then argv). A non-zero exit status fails the render: the header is not sent
and the error surfaces loudly.

 Per-provider system-prompt tuning, such as the strength of todo-guidance
 (`yca.provider.*.prompt.todo`), is covered in
 xref:features/todo-guidance.adoc[Todo and plan guidance].

 Iteration bounds and the exploration-plateau guard (per-model / per-provider /
 global cascade) are covered in
 xref:features/iteration-guards.adoc[Iteration guards].

A provider's context window (`yca.provider.*.contextWindow`) accepts an explicit
token count; when zero or negative (the default) it is auto-detected from the
provider `/v1/models` vendor extensions, cached one day per provider and model,
falling back to 128000 when nothing is found. Detected values are totals (prompt
+ completion combined); the pruning and compaction thresholds (`yca.pruning.*`,
`yca.compaction.*`) are computed against that window minus an output headroom of
`min(20000, window / 4)` tokens. Context management behavior is detailed in
xref:features/context.adoc[Context management].

== Structural code graph doc tree

When `yca.structuralCodeGraph.docs` is enabled (default), the agent writes a
per-source-file markdown doc tree under the graph store (`yca.structuralCodeGraph.storeDir`),
mirroring the project source layout, with optional LLM enrichment
(`yca.structuralCodeGraph.enrich`). The layout, the plain-text symbol search and
the `index.bin` role are described in
xref:features/code-graph.adoc[Structural code graph], with the on-disk format in
xref:features/code-graph-index.adoc[Compact binary code graph index].

== Memory extraction

Durable knowledge (user preferences, project decisions, long-lived facts) is
extracted from each session's conversation into the shared memory files with a
dedicated LLM call (the `yca.model.memory` model, falling back to `compact`).

The extraction pipeline - when it runs, what it selects, the per-session
watermark, how failures degrade, and why session close never blocks on it - is
described in xref:features/memory.adoc[Memory] and covered in depth in
xref:features/sessions.adoc[Sessions and memory]. See the `yca.memory.*`
entries in the generated list below for the tunables.

== Custom agents

`yca.agents` defines named agents selected with `--agent <name>`, `/agent <name>`
or an `@<name> ` prompt prefix. Defining agents, the `yca.agents` JSON shape and
the sub-agent model routing (`spawn_subagent model=<reference>`) are documented
in xref:features/agents.adoc[Custom agents], with the `yca.agents` model
reference in the generated list below.

== Prompt template

The interactive CLI prompt line (`yca.prompt.template`) is rendered from a
Handlebars template. Empty falls back to the built-in prompt. Placeholders,
helpers, coloring and example templates are covered in
xref:features/prompt.adoc[Prompt templates].
