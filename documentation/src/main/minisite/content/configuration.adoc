Configuration is resolved from, highest priority first:

. CLI arguments: `--yca-<key> <value>` (for example `--yca-provider-model`). The
  `yca.` prefix may be omitted, so `--provider-model` works too.
. JSON file: `~/.yupiik/coding-agent/configuration.json` (override the location
  with the `yca.configuration.json` key)
. System properties: `yca.provider.model` style keys
. Environment variables: `YCA_PROVIDER_MODEL` style keys (dots/hyphens become
  underscores, uppercased)

The `provider` group supports multiple providers. Each entry has an `id` that is
referenced as `$<id>/<model>` anywhere a model is expected (main model,
`model.compact`, `model.prune`, code graph enrichment). `defaultProvider`
selects the active entry (blank falls back to the first, then to the implicit
`default` provider). A provider's optional `providerSpecificOptions` JSON object
is merged into every API call payload for it. For single-provider setups the
legacy flat scalars (`yca.provider.baseUrl`, `.apiKey`, `.model`, `.api`,
`.reasoningField`, `.contextWindow`, `.timeoutSeconds`) build the implicit
`default` provider.

A provider's `contextWindow` accepts an explicit token count; when zero or
negative (the default), it is auto-detected from the provider `/v1/models`
vendor extensions (`context_window`, `model_context_window`, `context_length`,
`max_model_len`, llama.cpp `meta.n_ctx`, or `meta.n_ctx_train` when smaller
than the default). Detected values are totals (prompt + completion combined);
they are cached one day per provider and model under
`<storageHome>/context-window/` and fall back to 128000 when nothing is found.
Detection failures are ignored. The pruning and compaction thresholds keep the
remaining window as headroom for completions.

== Structural code graph doc tree

When `yca.structuralCodeGraph.docs` is enabled (default), the agent writes a
per-source-file markdown doc tree under the graph store, mirroring the project
source layout. For each parsed file it emits a deterministic structural extract
(symbols and edges). When `yca.structuralCodeGraph.enrich` is enabled, each doc
also gains an asynchronous, serialized LLM `## Summary` section.

For example `src/main/java/acme/Order.java` produces
`<storeDir>/docs/src/main/java/acme/Order.java.md`. Symbols and relations are
exposed as plain text, so they can be searched by simply grepping the docs
directory (for instance with the built-in `grep` tool and
`path=<storeDir>/docs`) instead of reading the graph store. `graph.json`
remains the source of truth for call-graph tracing (`code_trace_calls`) and for
the incremental fingerprint re-indexing.

== Custom agents

`yca.agents` defines named custom agents. Each agent is mainly a prompt; its
instructions are injected on top of the base system prompt (rules, tools,
environment, project context, skills and memory are kept untouched). The `prompt`
is inline text, or a file path whose content is loaded (for example
`prompt=~/.yupiik/coding-agent/agents/reviewer.md`). A value is treated as a file
path when it expands to an existing regular file, otherwise it is used as inline
text.

.Example configuration.json
[source,json]
----
{
  "agents": [
    { "name": "reviewer", "prompt": "~/.yupiik/coding-agent/agents/reviewer.md" },
    { "name": "tester", "prompt": "You are a meticulous test author. Prefer table-driven tests and always run them." }
  ]
}
----

An agent is selected on `run` with `--agent <name>`, in the TUI with
`/agent <name>` (persistent until `/new`), or per-turn by prefixing a prompt with
`@<name> `.
