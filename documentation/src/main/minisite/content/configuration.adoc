Configuration is resolved from, highest priority first:

. CLI arguments: `--yca-<key> <value>` (for example `--yca-provider-model`). The
  `yca.` prefix may be omitted, so `--provider-model` works too.
. JSON file: `~/.yupiik/coding-agent/configuration.json` (override the location
  with the `yca.configuration.json` key)
. System properties: `yca.provider.model` style keys
. Environment variables: `YCA_PROVIDER_MODEL` style keys (dots/hyphens become
  underscores, uppercased)

The `provider` group (`yca.provider.*`) supports multiple providers. Each entry
has an `id` referenced as `$<id>/<model>` anywhere a model is expected (main
model, `model.compact`, code graph enrichment).
`yca.provider.defaultProvider` selects the active entry (blank falls back to the
first, then to the implicit `default` provider). A provider's optional
`providerSpecificOptions` JSON object is merged into every API call payload for
it (eg. `{"reasoning_effort":"high"}` for OpenAI, or an Anthropic extended-thinking
shape such as `{"thinking":{"type":"adaptive","display":"summarized"},"output_config":{"effort":"max"}}`
on an Anthropic-compatible gateway like Azure AI Gateway; an explicitly configured
reasoning shape fully overrides the implicit/variant-derived one). For
single-provider setups, the flat `yca.provider.*` scalars build the
 implicit `default` provider.

TIP: how yca shapes the request payload per provider/model - reasoning effort,
output budget, variants and the opencode parity reference - is documented in
<<features/provider-tuning.adoc,Provider tuning>>.

Each provider can also declare `backgroundModelOverrides` (same
`compact`/`prune`/`memory` shape as `yca.model`) to override the global
background models for the sessions running on it. Resolution per field:

- a non-blank, non-`inherit` value is that model: a bare name is the
  provider's own model (implicitly routed to this provider, even when it is
  not listed in `models`), a `$provider/model` reference keeps its explicit
  routing (eg. a small local provider borrowing a remote summarizer);
- the `inherit` keyword resolves the global `yca.model.*` chain instead
  (including its `memory` -> `compact` and `prune` -> `compact` fallbacks);
- a blank value (the default) means the provider's own default model, ie. no
  dedicated background model for this provider.

A provider-level entry wins over the global one field by field, so a provider
can override `compact` while `inherit`ing `memory`. Code graph enrichment
(`yca.structural-code-graph.model`) keeps its own explicit override; when unset
it follows the default provider's `backgroundModelOverrides.compact`, then the
global chain.

A provider's `dynamicHeaders` are handlebars templates rendered into every
request to that provider (chat, streaming and models). They are resolved in
core (the llm client stays vendor-agnostic: it receives a per-request header
customizer from the caller). Each template is compiled once per provider and
re-rendered per request; a rendered blank value is skipped and a dynamic header
wins over the static `headers` map and over the default API-key authorization
when it targets the same name. The `exec` helper runs a command and returns (by
default stripped) stdout:

[source,json]
----
{
  "provider": {
    "dynamicHeaders": {
      "authorization": "Bearer {{exec \"exec_options=ttl=3600,strip=true\" \"MY_ENV=foo\" \"MY_OTHER_ENV=bar\" \"somebin\" \"somearg\" \"someotherarg\"}}"
    }
  }
}
----

`KEY=VALUE` leading arguments are child environment entries, `exec_options` is
a comma-separated `key=value` list (`ttl=N` caches the stdout for N seconds
across renders and providers, `strip=true|false` trims the output, `strip`
defaults to `true`), and every remaining argument is the command line (command
then argv). A non-zero exit status fails the render: the header is not sent
and the error surfaces loudly.

== Codex (ChatGPT subscription) providers

Codex-flavored providers talk to OpenAI's ChatGPT subscription backend
(`https://chatgpt.com/backend-api/codex`, the Responses API the Codex CLI uses)
instead of the pay-per-token public API. They are authenticated with an OAuth
signed-in ChatGPT account rather than an API key, and their models are included
with the subscription.

Set the base URL to `https://chatgpt.com/backend-api/codex` (or the full
`.../codex/responses`). The `api=auto` flavor detection recognizes the `/codex`
path and derives the chat endpoint `.../codex/responses`. The `model` id is the
slug of one of the models your plan exposes - the Codex model family varies by
subscription and over time (`gpt-6-luna`, `gpt-5.3-codex`, ...), so pick a slug
from what `/codex login` lists for your account (the exact set is fetched live
from the `.../codex/models` catalog):

[source,json]
----
{
  "provider": {
    "providers": [
      {
        "id": "codex",
        "baseUrl": "https://chatgpt.com/backend-api/codex",
        "api": "auto",
        "model": "gpt-6-luna",
        "contextWindow": 400000,
        "providerSpecificOptions": "{\"codex_client_version\": 160}",
        "dynamicHeaders": "authorization: Bearer {{codexAuth \"codex\"}}",
        "headers": "ChatGPT-Account-Id: xxxx-yyyy-zzzzz\nOpenAI-Beta: responses=experimental\noriginator: codex_cli_rs\naccept: text/event-stream"
      }
    ]
  }
}
----

`dynamicHeaders` and `headers` are properties-text strings: one `Name: value`
per line, newline (`\n`) separated - not JSON objects. The default `{{exec}}`
helper works exactly as described above.

The ChatGPT backend requires three extra request headers that are not sent by
default, so declare them in the provider `headers` string: `OpenAI-Beta:
responses=experimental`, the lowercase `originator: codex_cli_rs` (the backend
is case-sensitive about this one - a valid bearer or assertion still gets an
HTTP error without it), and `accept: text/event-stream` (every codex call is
streaming). These apply to both the regular and the enterprise flows.

The `{{codexAuth "<providerId>"}}` handlebars helper resolves the OAuth session
access token for that provider and returns it raw (prepend `Bearer ` in the
template). It refreshes lazily - only when a request is actually made - and
persists the (possibly rotated) refresh token to
`<storageHome>/providers/<provider>/codex.auth.json`.

=== Enterprise / company (Agent Identity) plans

Managed/company workspaces (Team, Business, Enterprise) are not reachable with
the plain OAuth browser/device login: their workspace policy rejects the
delegated-access login (`3p_delegated_access_policy_denied`). Codex signs those
accounts into a separate *Agent Identity* flow - a registered device identity
whose requests are authenticated with a signed `AgentAssertion` header instead
of a bearer token.

Enroll a provider with the `--enterprise` flag:

[source]
----
/codex login <provider> --enterprise
----

This runs the OAuth login first, then registers a fresh Ed25519 identity with
OpenAI's auth API (agent runtime + run task) and persists it next to the OAuth
tokens. Once enrolled, the provider authenticates every request with the
signed assertion. Configure the provider headers using the two extra helpers:

[source,json]
----
{
  "provider": {
    "providers": [
      {
        "id": "codex",
        "baseUrl": "https://chatgpt.com/backend-api/codex",
        "api": "auto",
        "model": "gpt-6-luna",
        "dynamicHeaders": "authorization: {{codexAgentAssertion \"codex\"}}",
        "headers": "OpenAI-Beta: responses=experimental\noriginator: codex_cli_rs\naccept: text/event-stream\nChatGPT-Account-ID: {{codexAccountId \"codex\"}}"
      }
    ]
  }
}
----

`{{codexAgentAssertion "<providerId>"}}` renders the full
`AgentAssertion {...}` header value (use it as `authorization`, no leading
`Bearer `). `{{codexAccountId "<providerId>"}}` renders the account id for the
`ChatGPT-Account-ID` header - from the agent identity when present, else from
the OAuth session - so you never need to hardcode it. A plain OAuth session
(no `--enterprise`) rejects `{{codexAgentAssertion}}` with a message telling you
to enroll first. As with the regular flow, `dynamicHeaders` and `headers` are
`Name: value` properties-text strings, not JSON objects.

For FedRAMP accounts the enrollment also stamps `X-OpenAI-Fedramp: true` and
every signed request carries the matching account id.

`providerSpecificOptions` may carry `codex_client_version`, the whole part of
the Codex CLI version this provider advertises for model gating in the Codex
backend catalog (eg. `160` for `0.160.x`, or `200` for `0.200.x`). It is an
internal option: it is consumed by the dialect when listing models and is never
sent on the wire. Omit it for the default of `160`.

== Custom authentication and headers

A provider authenticates with HTTP headers, resolved per request in this order,
highest priority last:

. the default `Authorization: Bearer <apiKey>` header sent from `apiKey`;
. the static `headers` map (fixed `Name: value` pairs);
. the `dynamicHeaders` map - handlebars templates rendered at each request.

A header targeting the same name wins over the lower-precedence ones, so a
`dynamicHeaders` (or static `headers`) entry named `authorization` replaces the
default `apiKey` header. Rendered blank values are skipped.

Out of the box the providers have these helpers available in a `dynamicHeaders`
template:

- `{{exec ...}}` runs a command and returns its stdout (cached with the
  `exec_options=ttl=...` option) - for token commands and short-lived secrets;
- `{{codexAuth "<providerId>"}}`, `{{codexAgentAssertion "<providerId>"}}` and
  `{{codexAccountId "<providerId>"}}` resolve the Codex OAuth / Agent Identity
  session, as described in the sections above.

When none of the built-ins fit your signing flow (a gateway-scoped token, a
lease-based credential, a corporate SSO dance), you can register your own
handlebars helper: implement a small
`CustomDynamicHeaderTemplateHelper` bean and inject it through the agent
container. A complete walkthrough - including a signed-header example and the
matching provider configuration - is in
xref:features/custom-headers.adoc[Custom headers].

The models a subscription exposes often come with per-model behavior or
variants (eg. reasoning-effort presets for a `gpt-6-luna`). Declare them under
`provider.models`, each entry matching by id or substring, with per-model
`contextWindow` and a `behavior` carrying `variants` selected at runtime with
`/model <model> <variant>`:

[source,json]
----
{
  "provider": {
    "providers": [
      {
        "id": "default",
        "baseUrl": "https://chatgpt.com/backend-api/codex",
        "model": "gpt-6-luna",
        "models": [
          {
            "model": "gpt-6-luna",
            "contextWindow": 400000,
            "behavior": {
              "variants": [
                { "name": "default", "reasoningEffort": "medium" },
                { "name": "reasoning", "reasoningEffort": "xhigh" }
              ]
            }
          }
        ]
      }
    ]
  }
}
----

Login is a one-time interactive step: run `/codex login <provider>` in a
session. It starts the ChatGPT/Codex OAuth browser flow (the default, matching
`codex login`; `--device` opts into the device-code flow like the CLI's
`--device-auth`), prints the URL to open, waits for you to authorize, and
persists the session token. If the device-code flow is disabled for the account
(device sign-in off in ChatGPT security settings), the login explains that you
can use the default browser flow instead. The models listed for the provider
are the ones your plan actually exposes, so use the slug that appears there
rather than a hardcoded example.

 Per-provider system-prompt tuning, such as the strength of todo-guidance
 (`yca.provider.*.prompt.todo`), is covered in
 xref:features/todo-guidance.adoc[Todo and plan guidance].

 Iteration bounds and the exploration-plateau guard (per-model / per-provider /
 global cascade) are covered in
 xref:features/iteration-guards.adoc[Iteration guards].

A provider's context window (`yca.provider.*.contextWindow`) accepts an explicit
token count; when zero or negative (the default) it is auto-detected from the
provider `/v1/models` vendor extensions, cached one day per provider and model,
falling back to 128000 when nothing is found. Detected values are totals (prompt
+ completion combined); the pruning and compaction thresholds (`yca.pruning.*`,
`yca.compaction.*`) are computed against that window minus an output headroom of
`min(20000, window / 4)` tokens. Context management behavior is detailed in
xref:features/context.adoc[Context management].

== Structural code graph doc tree

When `yca.structuralCodeGraph.docs` is enabled (default), the agent writes a
per-source-file markdown doc tree under the graph store (`yca.structuralCodeGraph.storeDir`),
mirroring the project source layout, with optional LLM enrichment
(`yca.structuralCodeGraph.enrich`). The layout, the plain-text symbol search and
the `index.bin` role are described in
xref:features/code-graph.adoc[Structural code graph], with the on-disk format in
xref:features/code-graph-index.adoc[Compact binary code graph index].

== Memory extraction

Durable knowledge (user preferences, project decisions, long-lived facts) is
extracted from each session's conversation into the shared memory files with a
dedicated LLM call (the `yca.model.memory` model, falling back to `compact`).

The extraction pipeline - when it runs, what it selects, the per-session
watermark, how failures degrade, and why session close never blocks on it - is
described in xref:features/memory.adoc[Memory] and covered in depth in
xref:features/sessions.adoc[Sessions and memory]. See the `yca.memory.*`
entries in the generated list below for the tunables.

== Custom agents

`yca.agents` defines named agents selected with `--agent <name>`, `/agent <name>`
or an `@<name> ` prompt prefix. Defining agents, the `yca.agents` JSON shape and
the sub-agent model routing (`spawn_subagent model=<reference>`) are documented
in xref:features/agents.adoc[Custom agents], with the `yca.agents` model
reference in the generated list below.

== Prompt template

The interactive CLI prompt line (`yca.prompt.template`) is rendered from a
Handlebars template. Empty falls back to the built-in prompt. Placeholders,
helpers, coloring and example templates are covered in
xref:features/prompt.adoc[Prompt templates].
