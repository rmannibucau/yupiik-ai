= Compaction and compression
:minisite-breadcrumb: Home[index.html] > Features > Compaction and compression
:minisite-nav-prev-link: context.html
:minisite-nav-prev-label: Context management
:minisite-nav-next-link: memory.html
:minisite-nav-next-label: Memory

yca reduces the context sent to the model with two independent layers:

* **core compaction** - deterministic, always available, and triggered near the
  model window;
* **compression** - model-invoked, DCP-like, and enabled by default, with
  absolute nudge thresholds at `50k` and `100k` tokens.

A third layer, **pruning**, is the legacy yca mechanism and is opt-in.
The layers compose: compression keeps the working context small, core
compaction is the last resort near the window limit, and pruning remains
available for deterministic local clearing.

== The two layers at a glance

[mermaid]
....
flowchart TD
    A["Stored conversation"] --> B{"yca.compression.enabled?"}
    B -->|"yes"| C["Apply active compressed blocks"]
    B -->|"no"| D["Send stored history"]
    C --> E["Estimate context tokens"]
    D --> E
    E --> F{"context >= contextLimit.max?"}
    F -->|"yes"| G["MUST compress nudge"]
    F -->|"no"| H{"context >= contextLimit.min or iteration threshold?"}
    H -->|"yes"| I["Soft or iteration nudge"]
    H -->|"no"| J["Normal turn"]
    G --> K["Model calls compress"]
    I --> K
    K --> L["Validate refs, ranges and protection"]
    L --> M["Flatten consumed blocks and store the new block"]
    M --> C
    E --> N{"context >= window - max(15%, 16k)?"}
    N -->|"yes"| O["Core compaction: summary + verbatim tail"]
    O --> D
....

The model never edits the transcript.
Compressed blocks and compaction summaries are applied when the outgoing
request is built, so the full session stays on disk and can be replayed or
inspected at any time.

== Core compaction

Core compaction is the deterministic fallback and exists in every mode.
It fires when the estimated prompt size reaches the window minus a safety
buffer:

[source,text]
----
trigger = context window - max(15% of the window, 16000 tokens)
----

On a 1M-token model the trigger is at `850k` tokens.
On a 128k-token model it is at `108.8k` tokens.
The trigger uses the raw context window with a safety buffer that leaves room
for the completion, then clamps to the usable window (the context window minus
the declared output-token reserve), so the gauge can never sit above 100%
without tripping an automatic compaction.

When it fires, yca summarizes the old conversation, keeps a verbatim tail
(`yca.compaction.tail.budgetTokens`, default `15000`), and replaces the old
messages in the outgoing request only.
The summary model resolves through `backgroundModelOverrides.compact`, then
`yca.model.compact`, then the session model.
If the provider rejects the request because the input is too large, yca
compacts once and retries the request; if the retry still overflows, the
oldest tail messages are spliced to their head and tail
(`yca.compaction.tail.overflowSpliceChars`, default `500`).
A transient summarizer failure (5xx/network after retries and the optional
main-model fallback) skips the pass and keeps the raw context so the next
automatic compaction retries from a clean state, unless the compaction was
requested with the `urgent` option below.

=== LLM-free compaction mode

When a provider must never pay a summarizer call, set the global
`yca.compaction.mode=no_llm` or a per-provider
`providers.<id>.compaction.mode=no_llm`. The mode is a tri-state enum:
`llm` (default) uses the LLM summarizer, `no_llm` runs only local
strategies and never calls a model, and `auto` inherits (for the global
configuration it resolves to `llm`, for a provider block it inherits the
global value). Compaction then runs only local strategies and
never calls an LLM:

1. the old tool-output prune (`yca.pruning.*`: shrink to
   `shrinkOutputChars`, clear to a marker once `minPruneTokens` are
   reclaimable),
2. the head+tail splice spill (`yca.compaction.tail.overflowSpliceChars`)
   toward the same trigger,
3. a tighter splice (halved cap) when the pass is `urgent`/overflow-driven.

The DCP-style structural strategies (dedup, write superseding, error-input
purge) run at the compaction checkpoint instead of the pruning checkpoint, so
they fire at the moment they matter. The compaction gate, the overflow
recovery and the window clamp keep working exactly as in the LLM path.

Because nothing is folded into a digest, the history grows monotonically
(spliced messages stay in place rather than being summarized away) - the right
trade for large-window providers that want zero background spend, and a
stronger loss on small windows. Speculative compaction is always off under
`no_llm` (it is LLM-backed by design). `yca.compaction.enabled=false`
still wins over the mode.

=== Manual compaction

`/compact` runs the same compaction on demand:

[source,text]
----
/compact [force] [urgent] [keep=<n>]
----

`force` bypasses the within-budget guard so compaction runs even below the
thresholds (tighter keep floors, halved tail budget).
`keep=<n>` raises the verbatim tail floor to at least `n` recent messages
(0 = the configured default).
`urgent` opts into a destructive fallback: when the summarizer fails
transiently after all retries and the optional main-model fallback, an urgent
compaction truncates the old messages locally instead of skipping the pass, so
a user explicitly reclaiming context near the window edge is never left stuck
above the budget by a flaky provider.
Without `urgent`, a summarizer failure keeps the raw context untouched and
reports the failure.

== Compression

Compression is the DCP-like layer.
It is enabled by default and exposes one model-callable tool, `compress`.
The model chooses a **closed** section of the conversation and writes the
summary itself; yca validates the range, protects the configured content,
replaces the range with a block in the outgoing request, and stores the block
for later turns.

Compression adds no summarizer call: the summary is part of the tool call.
The full transcript is never modified.

=== Message and block references

Every message carries a stable reference derived from its message id:
`@12@`, `@13@`, and so on.
References survive appends, restarts, and compactions.
Compressed blocks use a separate monotonic namespace: `@b1@`, `@b2@`, and so on.
The same block keeps its id for its whole life, and ids are never reused.

A tool call therefore looks like this:

[source,json]
----
{
  "topic": "quota NPE investigation",
  "content": [
    {
      "startId": "@12@",
      "endId": "@40@",
      "summary": "Exhaustive record of the session with the user intent, decisions, files, errors and next steps."
    }
  ]
}
----

If the range includes a block, the summary must include the block placeholder
exactly once, for example `@b2@`.
The server expands the placeholder with the stored block summary and flattens
the result, so a block never nests another block at request time.
If the model forgets a required placeholder, yca appends the missing block
summary under a short heading instead of silently dropping information.

=== Block lifecycle

[mermaid]
....
stateDiagram-v2
    [*] --> Active: compress creates bN
    Active --> Superseded: folded into a newer block
    Active --> Decompressed: decompress
    Active --> Absorbed: core compaction covers the range
    Superseded --> Absorbed: core compaction covers the range
    Decompressed --> [*]
    Absorbed --> [*]
....

* **active** - the block is applied to the outgoing request.
* **superseded** - a later compression replaced this block with a flattened
  summary that includes it; the old block is kept for audit.
* **decompressed** - the original messages are sent again; only allowed while
  the block is active.
* **absorbed** - a core compaction summarized the same span; the digest now
  carries the content, so the block is no longer applied.

=== A compression round

[mermaid]
....
sequenceDiagram
    participant M as Model
    participant Y as yca
    participant S as Session store
    M->>Y: compress(topic, @12@..@40@, summary with @b2@)
    Y->>Y: validate refs, overlap and protection
    Y->>Y: expand @b2@ and flatten the summary
    Y->>S: save block b3 and the audit event
    Y-->>M: block b3 active, tokens saved
    Note over Y: the next request replaces @12@..@40@ with b3
....

=== Batching several ranges

A single `compress` call accepts an array of small, disjoint ranges, each with
its own `{startId, endId, summary}`.
To batch well, send two to four small ranges that do not overlap, ordered
roughly by start ref; this saves a round-trip without asking the model to
summarize a huge contiguous span.

Each range is validated independently.
A recoverable defect in one range - a missing or invalid ref, a reversed or
unreachable span, a range touching the system prompt or the live session-state
tail, an overlap with a protected turn or an existing active block - skips only
that range and folds a corrective nudge into the result.
The rest of the batch is still applied, and the result enumerates the skipped
ranges so the model can retry them next turn.
A route is rejected as a whole only when it is strictly unusable: compression
disabled, an empty `content` array, ranges that overlap each other in the same
call, or malformed entries.

=== Nudges

The model is nudged to compress when the context grows, but it is never forced
to do so; this is the same contract as DCP. The reported targets are proactive
*working-context* targets, not model capacity: staying below them keeps the
prompt lean and focused, so a low percentage of the usable window does not
cancel them - but meeting them only ever means compressing genuinely closed
ranges, never a whole-session `compact` or blocking active work.

[cols="1,1,2",opts=headers]
|===
|Key
|Default
|Purpose

|`yca.compression.contextLimit.min`
|`50000`
|Soft floor: below it, turn and iteration reminders are off.
Accepts tokens or a percentage of the context window.

|`yca.compression.contextLimit.max`
|`100000`
|Strong working-context floor at which a stronger compression reminder
fires. Accepts tokens or a percentage.

|`yca.compression.contextLimit` per-provider (`yca.provider.providers[i].compaction.contextLimit.min`/`.max`)
|inherits global
|Per-provider override of the compress context limits; a null (absent)
field inherits the global value, so one provider can raise its soft/hard
floors (for example to `250000`) without affecting others.

|`yca.compression.iterationNudgeThreshold`
|`15`
|Sends the soft reminder after this many rounds since the last user message.

|`yca.compression.nudgeFrequency`
|`5`
|Repeats the strong reminder every N real LLM request rounds while above the
limit, and serves as the post-compression cooldown length so a successful
`compress` is not immediately re-hammered.

|`yca.compression.summaryBuffer`
|`true`
|Active summary tokens extend the effective `maxContextLimit`
(`baseMax + summaryTokens`), so an already-condensed working set is not
immediately re-flagged. This is a guidance target only: summaries still count
toward real context usage and the compaction guard is unchanged.
|===

The system prompt tells the model to evaluate signal-to-noise regularly, to
compress when a section is genuinely closed, and not to compress active work.
The nudge is a message, not a harness-side compaction: a model that ignores it
keeps its full context until the core trigger fires. A soft reminder and a
strong reminder are emitted on separate cadences (see above), and the
`/context` preview never advances either cadence - a preview is read-only.

=== Protection

Compression must not lose the information the next turn depends on.

[cols="2,1,3",opts=headers]
|===
|Key
|Default
|Effect

|`yca.compression.protectedTools`
|`spawn_subagent`, `skill`, `write_todo`
|Completed outputs of these tools inside the range are appended to the summary.

|`yca.compression.protectUserMessages`
|`false`
|When `true`, user messages inside the range are appended verbatim to the
summary. Protected user messages get a `BLOCKED` reference and cannot be
included in a range in the first place.

|`yca.compression.protectTags`
|`false`
|When `true`, `<protect>...</protect>` blocks are extracted and appended to the
summary.

|`yca.compression.turnProtection.enabled`
|`false`
|Refuse ranges that cover the most recent
`yca.compression.turnProtection.turns` turns (default `4`).

|`yca.compression.strategies.deduplication.enabled`
|`true`
|Before storing the block, identical tool calls inside the unpruned history are
collapsed to their latest occurrence.

|`yca.compression.strategies.purgeErrors.enabled`
|`true`
|Inputs of failed tool calls older than
`yca.compression.strategies.purgeErrors.turns` (default `4`) are marked for
pruning; the error message is preserved.
|===

== Without compression: core-only mode

Set `yca.compression.enabled=false` to disable the DCP-like layer completely:

* the `compress` tool is not registered;
* the context-management system prompt is not injected;
* the `50k`/`100k`/iteration nudges are not emitted;
* active blocks are no longer applied (they remain stored and apply again if
  compression is re-enabled);
* only core compaction remains.

This is deliberately the same behavior as opencode core without DCP.
On a 1M-token window, a session at `290k` tokens does not compact and keeps
growing until the `850k` trigger; the earlier free-model incident is exactly
this case.
Use it when predictability matters more than the working-context reduction.

[source,json]
----
{
  "yca": {
    "compress": {
      "enabled": false
    },
    "compaction": {
      "enabled": true,
      "buffer": { "percent": 15, "minTokens": 16000 },
      "tail": { "budgetTokens": 15000 }
    }
  }
}
----

== Legacy pruning

Pruning is the original yca mechanism: it never calls the LLM and clears old
tool outputs at `yca.pruning.thresholdPercent` (default `65` when enabled).
It is **disabled by default** in the aligned configuration, because
compression replaces its role.
Enable it explicitly when you want deterministic local clearing alongside, or
instead of, compression:

[source,json]
----
{
  "yca": {
    "compress": {
      "enabled": false
    },
    "compaction": {
      "thresholdPercent": 80
    },
    "pruning": {
      "enabled": true,
      "thresholdPercent": 65,
      "nudgeThresholdPercent": 55
    }
  }
}
----

The deduplication and failed-input purge strategies live in the compression
pipeline when compression is enabled, and in the prune branch when only pruning
is enabled.

== Choosing a mode

* **Large windows (`>= 128k`), long autonomous sessions** - keep the defaults:
  compression on, core compaction on, pruning off.
  The `100k` working-context reminder keeps the lean prompt an order of
  magnitude below the window, and core compaction remains the hard stop near
  the limit. The reminder is acknowledged to the model as a proactive
  working-context target, not an out-of-memory alarm.
* **Small windows (`<= 64k`)** - the absolute `50k`/`100k` thresholds are
  above the window, so compression cannot fire before core compaction.
  Either accept core compaction or use percentages, for example
  `"contextLimit": { "min": "25%", "max": "40%" }`, with a smaller
  `yca.compaction.tail.budgetTokens`.
* **Deterministic-only operation** - disable compression and keep core
  compaction; this is the behavior users coming from opencode without DCP
  expect.
* **Legacy yca behavior** - disable compression, enable pruning, and keep
  `yca.compaction.thresholdPercent` at `80`.

== Manual control and inspection

The `/context` command still dumps the transcript, the exact LLM payload and
the next request.
`/compact` performs an immediate core compaction.
The `compress` tool's `status` and `decompress` actions manage blocks from the
model side, and the same information is available in the TUI and web usage
gauges.

== Persistence

The transcript is append-only.
Compressed blocks and their audit events are stored next to the session, so a
restart rebuilds the outgoing request without re-running the model.
Disabling compression mid-session stops applying blocks but does not delete
them; re-enabling restores them.
A core compaction that covers a block marks it `absorbed`, and a later
compression that includes a block marks it `superseded`; neither case can lose
the block's text because summaries are flattened before they are stored.

== Migrating from `manage_context`

`compress` replaces the model-facing `manage_context` tool.
`manage_context` remains readable in old transcripts, but new sessions expose
`compress` only.
The old `yca.tools.manageContext.enabled` key is accepted as an alias for
`yca.compression.enabled` for one minor release, with a deprecation warning.
The old 30% floor, whole-context compact and generic prune actions are
superseded by the range-based `compress`, the `compact` escape hatch and the
legacy pruning layer respectively.

=== Speculative compaction

By default, compaction is synchronous: when the context reaches the trigger, the turn pauses while the summarizer runs.
For long tool-heavy tasks this pause can be significant.

Speculative compaction (opt-in) computes the summary in the background before the trigger is reached, while foreground inference continues:

[source,json]
----
{
  "yca": {
    "compaction": {
      "speculative": { "policy": "concurrent", "startPercent": 80 }
    }
  }
}
----

* `speculative.policy` is `off` by default: the existing synchronous behavior is preserved, and no background work of any kind is started.
  Set it to `concurrent` only when the effective provider/model routing accepts overlapping requests: a single-slot local inference server cannot run a background summarizer without delaying the foreground request, so moving the call earlier would not save latency.
* `speculative.startPercent` is the percentage of the automatic compaction trigger at which the background summary starts (1-99, default 80).
  Example: with a 100k-token trigger and the default 80, speculation launches around 80k estimated prompt tokens.

Guarantees, whichever the configuration:

* Only the foreground compaction checkpoint replaces the live history, persists it and reports the reduction; the background job only computes a summary.
* A candidate summarizes an exact prefix of the history. At adoption time that prefix is compared with the live history: any change (edit, prune, metadata change) rejects the candidate and the normal synchronous compaction runs instead.
* Messages appended while the background summary was running (tool results, user input) are preserved at adoption.
* A failed or cancelled speculation never touches the history: no local truncation fallback is installed from a background job.
* The pre-compaction hook gate is checked both at launch (a veto means no launch) and at adoption (a veto discards the candidate; the synchronous path then applies its own gate).
* Background summarizer calls are billed exactly once as auxiliary usage, at the call itself; adoption adds no usage.

Speculation state is scoped to a single agent run: it is discarded when the run exits, is cancelled, or the session closes.
A late remote inference completing after cancellation is never installed.
