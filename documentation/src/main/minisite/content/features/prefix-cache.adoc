= Provider prefix cache

Most OpenAI-compatible backends cache the KV state of a request prefix and
reuse it for later requests that share the same leading tokens. A hit costs a
fraction of a full re-process (and on metered providers, a fraction of the
price), so yca is built to keep that reusable prefix **byte-identical across
every request of a session**.

== How providers cache

[cols="1,2,3",opts=headers]
|===
|Backend
|Mechanism
|What breaks it

|SGLang (RadixAttention)
|Automatic KV-cache reuse over a radix tree of token prefixes; hits can be partial.
|Any divergence in the serialized token prefix; page-size (block) alignment; landing on a worker that does not hold the prefix.

|vLLM (Automatic Prefix Caching)
|Reuses KV blocks for matching token prefixes; non-matching suffixes are reprocessed.
|A change (or an inserted note) early in the conversation reduces the shared token prefix; tokenizer/chat-template drift; cache eviction and scheduling.

|OpenAI
|Automatic prompt caching on supported models, with eligible cache boundaries.
|Changing early instructions, the tools array, or message serialization reduces the reusable cached prefix.

|Anthropic
|Explicit `cache_control` breakpoints.
|Changing content before a breakpoint invalidates reuse of that breakpoint's prefix.

|Google Gemini
|Implicit caching on supported models plus explicit context caching.
|Changing the request prefix reduces implicit reuse; explicit cached content must stay stable.
|===

The common rule across all of them:

[quote]
Keep the reusable prefix identical across requests. Put dynamic instructions and
user-specific content afterward.

yca targets that rule structurally, so the guarantees below apply to any of
these backends.

== What yca guarantees

* **Stable head.** The system prompt and the tools array are serialized in a
  fixed order with fixed fields; nothing in them varies per round-trip. The
  tools schema, `tool_choice`, `max_tokens` and the other request parameters
  are identical for every call of a session, because some providers re-key the
  cache when the *whole request header* changes, not just the messages.
* **Append-only conversation.** Messages are only ever appended between
  round-trips. yca never rewrites, reorders or trims a message that was already
  sent - a mid-conversation edit of an earlier message would invalidate every
  cached block after the edit point.
* **No system messages mid-conversation.** The `system` role appears exactly
  once, as the first message. Injection-style helpers must not append `system`
  messages into the flow: on several backends (verified on SGLang-served
  deepseek endpoints) a trailing or interleaved `system` message deserializes
  the prompt differently and drops the cache back to the static prefix
  (~2k tokens), even though the bytes before the note are unchanged. The same
  note carried as a `user` or `assistant` message keeps the cache intact.
* **Notes ride at the tail.** When yca must tell the model something
  mid-session (for example that a file it read earlier has changed on disk),
  the note is folded into the tool result of the very action that caused it -
  after the stable prefix, inside brand-new content - so the cached part is
  unaffected and no extra message enters the flow.

== The stale-read note as a case study

When a `write_file`/`edit_file` invalidates the content of an earlier
`read_file`, yca flags the stale paths. Three designs were considered:

* Rewriting the earlier `read_file` result in place (replacing it with a bare
  marker) - this edits a message in the cached prefix, so every later block
  misses. Rejected.
* Appending the note as a separate message - append-only, but the note must
  then ride as a `user` message: measured on an SGLang-served deepseek
  endpoint, the same note as a `system` message deterministically drops the
  cache to the static prefix (~2k tokens) on every stale-read transition, while
  a `user` note keeps it. Workable, but still adds a message to the flow.
* Folding the note into the write tool's **own result** (shipped) - the write
  result is brand-new content that round, so announcing "wrote X; note: /a.txt
  is now stale, re-read it" costs zero cache tokens and injects no extra
  message at all. This is the design yca ships: the tool-result message is
  composed once at emission time, never rewritten afterwards.

== Extending yca without breaking the cache

If you add code that mutates the outgoing request list, keep the invariant:

. Serialize the system prompt and tools once and reuse them.
. Append messages; never rewrite, reorder or delete sent ones.
. Use only `user`/`assistant`/`tool` roles after the head; never a second
  `system` message.
. Keep per-request option fields (`max_tokens`, `tool_choice`, ...) constant
  across a session.
. When checking results, compare *cached-token counts* reported by the provider
  (usage blocks), not latency: page-aligned partial hits and cold worker caches
  make wall time misleading.

A one-shot verification recipe when in doubt: send request A twice, then A plus
the appended note twice, then diff the cached-token counts of the second send
of each pair. If the appended-note variant shows a cached count collapsing to
the static-prefix size, the note is being carried in a cache-hostile way.
