yca keeps a durable, cross-session memory so preferences and project decisions
survive individual conversations. This page explains how memory is *written*,
how it is *selected* into the model context, and how to tune it.

== Overview

[a2s]
....
                     WRITE (live, crash-safe)                    READ (session start only)
  turn ends ──► idle extraction (LLM) ─┐                         session opens / resume
  memory_write (explicit) ─────────────┤                             │
                                       ▼                             ▼
                              MemoryStore.append         BM25-lite ranking
                              (both paths, direct)       (global + project,
                                       │                  recency tie-break)
                                       ▼                             │
                              MEMORY.md files           greedy fill 50/50
                              (global + project,        + spillover <= maxChars,
                               capped maxLines)                 │
                                       │                          ▼
                                       │                 <memory> snapshot in the
                                       │                 stable prefix, cached ONCE
                                       │                 for the session lifetime -
                                       │                 file writes mid-session do
                                       └──►              NOT rewrite it (never re-read)
....

Memory lives in two scopes, persisted as markdown bullet lists:

* *Global* (`~/.yupiik/coding-agent/memory/MEMORY.md`) - durable user
  preferences and cross-project rules ("always use tabs", "never edit
  generated files").
* *Project* (`<project>/.yca/memory/MEMORY.md`) - project-specific decisions
  and knowledge.

Both files share the same simple format:

[source]
----
# Memory

Durable facts, decisions and preferences. One bullet per line.

- Always use tabs for indentation.
- The CLI must be backward compatible with v1.
- Run `mvn -q -pl tui -am package` to build the fat jar.
----

== Writing memory

=== Automatic extraction (default)

At the end of a turn, `MemoryExtractor` asks the model to distill the
conversation into at most 3 durable facts:

[source,json]
----
{
  "facts": [
    { "text": "...", "scope": "global" | "project" }  <1>
  ]
}
----
<.> Each fact pairs free text with a target scope (`global` or `project`); memory is stored per scope.

Extraction is:

* *idle* - runs asynchronously while yca waits for the next input, never
  blocking a turn,
* *best-effort* - failures are silent (memory is never corrupted),
* *throttled* - at least `memory.extractMinChars` (default 1000) characters of
  *new* text must accumulate before another extraction costs an LLM call,
* *deduplicated* - the watermark prevents re-processing already extracted
  excerpts, and `MemoryStore.append` skips exact duplicates,
* *live* - extracted facts are written directly to `MEMORY.md`
  (`MemoryStore.append`), crash-safe and immediately durable. Because the
  prompt's `<memory>` section is a session-frozen snapshot that is never
  re-read mid-session, this file write does not rewrite what the current
  session sees; the facts become visible to the <em>next</em> session (or a
  resume) which rebuilds the snapshot.

The extraction cadence (how often an extraction LLM call runs) is governed by
`memory.mode`:

* `FULL` - the every-N-turns cadence plus the todo-completion flush (N =
  `memory.extractEveryTurns`, default 3). Best when the memory model is a
  distinct, cheap model.
* `LAZY` - extract only when all todos are done (nothing pending) or at session
  close. Best when extraction runs on the session's own expensive model.
* `AUTO` (default) - pick per the routing: the memory model resolving to the
  same model as the current turn selects `LAZY`, a distinct/cheaper memory
  model selects `FULL`.

=== Manual write

The `memory_write` tool persists a fact immediately:

[source]
----
memory_write(fact: "The build uses Java 21.", scope: "project")
----

=== Near-duplicate replacement

`append` detects that a new bullet *supersedes* an existing one (normalized
token Dice similarity >= 0.8 with at least 4 shared tokens). The old wording is
replaced, not duplicated - so reformulations do not accumulate.

=== Deterministic cap

Each scope is capped at `memory.maxLines` (default 200) bullets. Beyond it,
the *oldest* bullets are dropped on write. This is a cheap, model-free floor
that prevents unbounded growth even when the LLM-based compaction is disabled
or below its size threshold.

=== LLM compaction (optional)

When the project file grows past 64 KB, `MemoryCompactor` can rewrite it with a
compact model: near-duplicates are merged, superseded and one-off facts are
dropped. A backup (`MEMORY.md.bak`) is kept, and rewrites reducing the file by
less than 20% are discarded. Enabled with `memory.compactEnabled` (default
true) - this is the *quality* counterpart of the deterministic cap (which
bounds size even when no model call is wanted).

=== Choosing the memory model

The memory write path uses a dedicated background model, configured through
`yca.model.memory` (same shape as `model.compact` and `model.prune`: an object
whose `name` is the model on this background path, plus optional sampling and
output tuning). When `name` is blank it falls back to the compact model, then
to the session provider model. A `$<provider>/<model>` reference pins it to a
specific provider - handy for running memory extraction on a cheap local model
(eg. llama.cpp) while the main conversation uses a remote provider.

=== Running memory on a local model (llama.cpp)

Memory extraction is a short, low-stakes call, so it is a good candidate to
offload to an in-house LLM. As an example, the local setup below serves a
1.7 B model with llama.cpp on a modest laptop GPU:

[cols="1,3", options="header"]
|===
| Component | Value

| GPU
| NVIDIA GeForce GTX 1650 Ti Mobile (Max-Q Design), 4096 MiB VRAM, 35 W TDP

| llama.cpp
| `0.4.1-dev` (build 11011, commit aa39d7a3e), Clang 19.1.7, Linux x86_64

| Model
| `unsloth/Qwen3-1.7B-GGUF:Q4_K_M` (28 layers, 2048 hidden, native ctx 40960)
|===

Serve it on port 8080 with the full model on the GPU, a 32 K context backed by
a quantized KV cache (that is what makes 32 K fit in 4 GiB), flash attention
on for speed, and one parallel slot:

[source,sh]
----
llama serve -hf unsloth/Qwen3-1.7B-GGUF:Q4_K_M \
  -ngl 28 --ctx-size 32768 --parallel 1 \
  --cache-type-k q8_0 --cache-type-v q8_0 \
  --batch-size 128 --ubatch-size 64 --flash-attn on \
  --host 127.0.0.1 --port 8080
----

`-ngl 28` keeps every layer on the GPU (the Q4 weights are ~1.1 GB); `parallel 1`
halves the KV cache; the `q8_0` KV quant + `flash-attn` keep 32 K context
inside the 4 GiB budget at roughly 70 tokens/s.

Point the *memory* background path at that server while leaving the main
session provider untouched, by declaring the local backend as an extra provider
and pinning `model.memory.name` to it with `$local/<model>`:

[source,json]
----
{
  "provider": {
    "providers": [
      { "id": "remote", "baseUrl": "https://api.openai.com/v1", "model": "gpt-5-mini" },
      {
        "id": "local",
        "baseUrl": "http://127.0.0.1:8080/v1",
        "api": "completions",
        "model": "$local/unsloth/Qwen3-1.7B-GGUF:Q4_K_M",
        "contextWindow": 32768
      }
    ]
  },
  "model": {
    "memory": {
      "name": "$local/unsloth/Qwen3-1.7B-GGUF:Q4_K_M",
      "temperature": 0.6,
      "top_p": 0.95,
      "top_k": 20,
      "max_tokens": 800
    }
  }
}
----

Set `contextWindow` to the served `--ctx-size` (32768) so the usage gauges and
the pruning/compaction thresholds match what llama.cpp can actually hold.
Sampling mirrors the Qwen3 recommendations (`temperature` 0.6, `top_p` 0.95,
`top_k` 20) and `max_tokens` bounds a single extraction. When the local backend
does not support the structured `{"facts":[...]}` schema, `MemoryExtractor`
automatically falls back to a plain compression snippet, so memory is never
lost.

== Selecting memory into context

At the start of a session, yca injects a `<memory>` section into the system
prompt, capped at `memory.maxChars` (default 2000) characters. It is built once
and never re-read mid-session, so the prefix stays byte-stable and provider
prompt caches keep hitting:

[source]
----
<memory>
<global>
- Always use tabs for indentation.
- Run `mvn -q -pl tui -am package` to build the fat jar.
</global>
<project>
- The CLI must be backward compatible with v1.
</project>
</memory>
----

=== Ranking

Both scopes are ranked with a *BM25-lite* scorer against a query built from the
latest user turn **plus** the current todo list, so durable facts relevant to
the active plan surface even when the last message is terse.

The selection is *greedy and scope-fair*:

1. fill global with its top entries up to 50% of the budget,
2. fill project with its top entries up to the other 50%,
3. spill the remaining budget to whichever scope has the most relevant
   leftovers (global first - directives are usually higher value).

=== Recency tie-break

Global facts are append-only: the newest durable facts sit at the tail of the
file, which head-bounded selection used to starve. The ranker applies a small
recency multiplier (at most +10%, tie-break only) to global bullets, so a
recently appended fact wins against an equally-relevant older one without
letting recency override relevance.

=== No-query fallback

When there is no ranking signal (a context dump, a resumed session, a bare
prompt), global keeps its head and project its head, capped at half the budget
each - deterministic and bounded.

=== Durable-directive floor

Global memory is never fully dropped: even when no global bullet matches the
query, the established head of the global file is still injected (up to
2/3 of the global half-budget). Relevance trims the stale tail, not the core
directives.

=== Frozen prompt snapshot, live files

The durable `<memory>` section is computed *once per session* from `MEMORY.md`
and cached as the session's prompt snapshot - the current session never re-reads
the files, so the system prefix stays byte-stable and provider prompt caches
keep hitting across every turn. Writing `MEMORY.md` (global or project)
mid-session is always allowed; it just never rewrites the snapshot. A fresh
session (or a resume) rebuilds the snapshot from the now-current files.

Because each *turn already contains the conversation* the facts were mined
from, there is no need to surface a newly-written fact back into the prompt:
the model that is about to answer has it in context. Memory writes are
therefore *live on disk, but invisible to the current session's snapshot* -
they are picked up read-only by the <em>next</em> session:

* `memory_write` and automatic extraction both persist directly to `MEMORY.md`
  immediately (`MemoryStore.append`), crash-safe and durable.
* The current session keeps its frozen `<memory>` snapshot unaffected, so the
  provider cache key (system + user prefix) stays byte-identical for the whole
  session.

The trade-off is that a fact written mid-session is not reflected in the
current session's prompt - only in the next session's (or a resume's) snapshot.
That is exactly what keeps the prefix cache hit; if a fact matters right away,
the conversation it came from already carries it.

== Configuration reference

[cols="2,1,2,2", options="header"]
|===
| Property | Default | Scope | Meaning

| `memory.mode`
| `AUTO`
| extraction
| Extraction cadence: `FULL` (every-N-turns + todo flush), `LAZY` (only when
  todos are done or at session close), `AUTO` (pick by whether the memory
  model == current model).

| `memory.enabled`
| `true`
| both
| Enable extraction and injection.

| `memory.maxChars`
| `2000`
| context
| Max chars of memory injected in the system prompt (built once per session).

| `memory.maxRatio`
| `0.2`
| context
| Memory budget is `min(maxChars, systemPromptCap * maxRatio)`; 0 = plain
  maxChars. Auto-disables memory below 1000 chars budget.

| `memory.maxLines`
| `200`
| store
| Deterministic per-scope cap; older bullets dropped on write.

| `memory.extractMinChars`
| `1000`
| extraction
| Min new text before an extraction runs.

| `memory.compactEnabled`
| `true`
| store
| LLM rewrite of the project file past 64 KB (>= 20% reduction kept).
|===

== Tips

* Memory is *ranked*, not dumped: with `maxChars=2000` the model sees the
  facts most relevant to the session start, not the oldest 2000 chars. If a
  relevant fact does not surface, enrich the todo list (it is part of the
  ranking query) or write it with `memory_write` right before it matters.

* `memory.maxLines` bounds the file with no model cost; `compactEnabled` keeps
  the file *clean* with a model cost. Both default on.

* The memory files are plain markdown - they can be edited by hand. The current
  session keeps its frozen prefix (it never re-reads mid-session); an external
  edit is picked up by the *next* session's prefix build.

* To disable memory entirely: `memory.enabled=false` (extraction is skipped
  too, nothing is written).
