= Permission modes
:minisite-breadcrumb: Home[index.html] > Features > Permission modes

yca gates tool calls behind configurable permission modes:

* `ask` prompts before each call that touches the system;
* `auto_edit` allows file edits without prompting;
* `yolo` (also spelled `all`) bypasses permission checks and allows all calls.

Allow/deny glob lists refine what the agent may touch in any mode: entries are
tool names (`bash`) or command patterns (`rm *`, `bash:rm -rf *`) matched
against every segment of a compound command, and a command is only allowed when
all its segments pass. Deny entries win over everything else.
Plan mode additionally hides the file-mutating tools (`edit_file`, `write_file`,
`apply_patch`) from the tool list the model sees, so plan turns cannot build.

== Modes at a glance

[cols="1,2,2,2", opts=headers]
|===
|Mode |Edits |Bash and other mutable tools |Read-only tools
|`ask` (default) |prompt |prompt |allowed silently
|`auto_edit` (alias `autoedit`) |allowed silently |prompt |allowed silently
|`yolo` (alias `all`) |allowed silently |allowed silently |allowed silently
|===

== Sample tools by category

[cols="1,2", opts=headers]
|===
|Category |Sample tools
|Edit (prompted in `ask`) |`write_file`, `edit_file`, `apply_patch`, `maven_repository_knowledge`
|Bash (prompted in `ask` and `auto_edit`) |`bash`, e.g. running `mvn install`, `rm -rf target` or `docker run -p 80:80 nginx`
|Read-only (never prompted) |`read_file`, `grep`, `glob`, `list_dir`, `read_symbol`, the `code_*` tools, `skill`, `webfetch`, `websearch`, `maven_knowledge_content`
|Agent (never prompted) |`write_todo`, `ask_user`, `manage_context`, `memory_write`, `spawn_subagent`, `check_subagents`
|Read-only bash rules (never prompted) |`git status`, `git diff`, `ls`, `grep`, `sed -n`, ... (see <<_bash_command_rules,Bash command rules>>)
|MCP (read-only calls never prompted, others follow the mode) |`<server>_<tool>`
|===

IMPORTANT: `yolo` bypasses the approval gate but not the deny list:
`yca.permissions.deny` (including denied bash segments) is enforced in every
mode, including `yolo`.
`yca.permissions.allow` and session grants are resolved before the mode, so they
behave the same in all three modes.

NOTE: This page covers the permission mode axis. The orthogonal plan/build axis
(`plan` is read-only) is covered in xref:modes.adoc[Plan and build modes].

== Bash command rules

Read-only commands do not need prompting: `yca.permissions.bash.rules` lists
the commands that are silently allowed, in both `plan` and `build` modes.
The defaults cover `git status`, `git diff`, `git log`, `git branch`, `git show`,
`git blame`, `git rev-parse`, `git merge-base`, `git ls-files`, `git cat-file`,
`git ls-tree`, `git for-each-ref`, `git name-rev`, `git describe`, `git stash list`,
`git submodule status`, `git remote` (except its write subcommands
`add`, `remove`, `set-url`, `rename`, `prune`), `xargs git log`, `ls`,
`cat`, `pwd`, `echo`, `find`, `grep`, `rg`, `wc`, `head`, `tail`, `test`,
`tr`, `sort`, `uniq`, `jq`, `sed -n` and `java -version`/`java -help`, plus the
read-only text processing and inspection families `awk`, `cut`, `diff` (except
`-o`/`--output`), `basename`, `dirname`, `stat`, `file`, `which`, `readlink`,
`realpath`, `du`, `df`, `id`, `uname`, `date` (except `-s`/`--set`), `env`,
`printenv`, `printf`, `nl`, `paste`, `column`, `seq`, `cksum`, `sum`, `md5sum`,
`sha256sum`, the archive inspection families `unzip -l`, `unzip -p`,
`unzip -Z`, `zipinfo`, `jar t`/`jar tf`/`jar tvf` and `tar t`/`tar tf`/
`tar tvf`/`tar tzf` (extraction and creation forms like `unzip dist.zip`,
`jar xf`, `tar xzf` are not allowlisted), and the GitHub CLI families `gh pr
view`/`gh pr checks`/`gh pr diff`/`gh pr list`, `gh issue view`/`gh issue list`,
`gh run list`/`gh run view`/`gh run watch` and `gh api`.

[cols="1,3", opts=headers]
|===
|Key |Description
|`matcher.commandStart.options` |Tokens the command must start with, matched token-wise so `git diff` does not match `git difftool`.
|`matcher.excludeOptions` |Tokens (or consecutive token sequences) that cancel the match, e.g. `sed` is allowed but `sed -i` is not.
|`plan` |Resolution in `plan` mode: `ask`, `auto_edit` or `yolo`/`all` (allowed without prompting).
|`default` |Resolution in `build` mode; when omitted it inherits `plan`.
|===

A command is silently allowed only when all its segments (`&&`, `||`, `;`,
`|` and newlines split them) match rules resolving to `yolo`/`all`.
Segments carrying redirections or substitutions (`>`, `<`, `$(...)`,
backticks) always fall back to the gate. Shell control keywords (`for`,
`while`, `if`, `do`, `done`, `fi`, ...) are syntax, not commands: they are
stripped from every segment before evaluation, so a loop body like
`do unzip -l $f 2>/dev/null` is evaluated (and reported, when denied) as
`unzip -l $f` and the tolerated `/dev/null` plumbing is dropped the same way -
a `do rm -rf $f 2>/dev/null` cannot hide from a `rm *` deny entry.
When a command is approved for the session, the grant uses the matched rule
`commandStart` tokens, so approving `docker run -p 80:80 nginx` grants
`docker run ...` and not every `docker` command.
Session grants are in-memory and cleared when the agent switches back from
`build` to `plan` mode: build-phase approvals never leak into planning.
The session approval mode is reset at the same time, so a `yolo`/`auto_edit`
selected for a build phase does not silently keep plan mode building; `plan`
falls back to the configured `yca.permissions.mode` (default `ask`) while an
explicit `/permissions yolo|auto_edit` in `plan` remains possible as a
deliberate override.
Crossing from `plan` to `build` sets the session approval mode to `auto_edit`:
build means "apply the work", so file edits apply without prompting while bash
commands still follow the plan/build rules or reach the gate. The override is
applied unconditionally - even over an explicit `/permissions` selection - and
the symmetric `build -> plan` reset always restores a clean plan posture;
switching `build -> build` keeps the current approval mode untouched.

When a bash command is not auto-allowed by the rules and reaches the approval
gate (in TUI/CLI), the modal detail explains *why* it is asked with a
`Why asked: segment 'git add -A' is not in the read-only bash families
(yca.permissions.bash.rules)` line naming the first failing segment. If the
user denies, that same cause is carried into the denial feedback the model
sees (`refused by the user: segment ...`); headless runs without an
interactive gate append the cause to the denial reason too. The gate flow
itself is unchanged: allow-once and allow-session approvals still work in
both modes.

The plan-mode system prompt summarizes the read-only families for the model
through `yca.permissions.bash.readOnlyPromptHints` (free text, defaulting to a
concise "git status/diff/log/show, ls, cat, grep, head, tail, ...; commands
that mutate repository state such as git add are denied" sentence). It is
curated prose rather than a dynamic render of `rules` for brevity and
scalability - the full rule list is long and per-workspace - and the rules
remain the enforcement gate. Set it to a blank string to omit the sentence.

[source,json]
----
{
  "permissions": {
    "mode": "ask",
    "bash": {
      "readOnlyPromptHints": "Plan-mode bash is limited to read-only command families (git status, git diff, git log, git show, ls, cat, grep, head, tail, ...); commands that mutate repository state such as git add are denied.",
      "rules": [
        {
          "matcher": { "commandStart": { "options": ["docker", "run"] } },
          "plan": "ask",
          "default": "all"
        }
      ]
    }
  }
}
----

With this rule, `docker run` prompts in `plan` mode but runs silently in
`build` mode.

TIP: the same rule can be set with flat properties, e.g.
`--yca-permissions-bash-rules-0-matcher-commandStart-options docker,run
--yca-permissions-bash-rules-0-default all` for the `run` command, or
`YCA_PERMISSIONS_BASH_RULES_0_MATCHER_COMMANDSTART_OPTIONS=docker,run` as an
environment variable.

See xref:../configuration.adoc[Configuration] for the permission options.
