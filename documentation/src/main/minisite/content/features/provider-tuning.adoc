How yca shapes the LLM request payload per provider and per model: reasoning
effort, output budget, sampling and the per-family implicit defaults. Includes
the wire comparison with opencode observed on a real proxy capture and the
measured parity benchmark (context and wall-clock) against opencode.

== What yca sends by default

See also link:opencode-free.html[experimental OpenCode free inference] for its dedicated transport and security limitations.

For every chat completion request yca resolves a per-model *budget*, a
*reasoning effort* and a *variant*. The resolution chain is (first match wins):

1. the explicit request/session value (eg. a `/model` command with a variant),
2. a value already merged in `providerSpecificOptions` (put-if-absent),
3. the selected per-model variant (`tuning.variants`, or its `defaultVariant`
   when the session selected none),
4. the configured reasoning effort (per-model `behavior` or provider-level
   `tuning.reasoningEffort`),
5. the model catalog default (`default_reasoning_level` from an
   OpenAI-compatible `/models` payload),
6. otherwise *absent* - there is no implicit per-family default anymore
   (Codex keeps its unconfigured `medium` fallback).

[a2s]
....
  request value
      |  (1)
  providerSpecificOptions (reasoning_effort already there?)
      |  (2)
  per-model variant tuning.variants[].reasoningEffort (or defaultVariant when none selected)
      |  (3)
  configured effort (behavior or provider tuning)
      |  (4)
  model catalog default_reasoning_level
      |  (5)
  absent (no implicit default; field not sent)
      |  (6)
  payload: { model, messages, tools, reasoning_effort?, store:false, max_tokens?, ... }
....
== Reasoning effort

Some models expose a reasoning effort tier (deepseek-v4, gpt-5, gemini
thinking). yca mirrors opencode's tuning concept:

- `tuning.reasoningEffort` at provider level, or per-model in `models[].behavior` /
  `models[].tuning` - accepted values depend on the family, typically
  `none`, `low`, `medium`, `high` (and `max`/`xhigh` for the families that
  support them);
- unset leaves the field absent on the wire unless the model catalog advertises a
  default: the provider default applies, with no implicit per-family tier
  injected by yca (deepseek-v4 is *not* forced to `max`, gpt-5 is *not* forced
  to `medium`). Reasoning is an explicit opt-in or a catalog capability, never a
  surprise.
- an OpenAI-compatible model listing can advertise the capabilities itself:
  `supported_reasoning_levels` populates the `/model` variant picker with the
  exact efforts the model accepts, and `default_reasoning_level` supplies the
  effort sent when nothing is configured. Codex exposes both fields and yca
  forwards them from its catalog; Responses/Completions backends that return
  them get the same behavior. Configured variants and `reasoningEffort` always
  win, and a listing without these fields keeps the previous behavior.

[NOTE]
.No catalog merge
Configured variants replace the catalog ones entirely, and a configured effort
replaces the catalog default. The two facets are independent, so setting a
variant does not prevent the catalog default from applying when no variant is
selected. Codex without any catalog metadata still defaults to `medium` (its
backend streams no reasoning otherwise); other OpenAI-compatible wires leave the
field absent.

[NOTE]
.Why there is no implicit default
Historically yca injected a per-family effort (notably deepseek-v4 -> `max`),
mirroring opencode's strongest-profile default. That is expensive: on
deepseek-v4 a single call can emit tens of thousands of reasoning characters.
Today the field is simply absent unless you configure it - opencode parity on
the wire and the leanness that gave, see <<benchmark-parity>>. Set
`reasoningEffort` explicitly (e.g. `medium`) when a task genuinely benefits
from chain-of-thought.

== Opt-in reasoning replay

For compatible Chat Completions servers such as Qwen, set `capabilities.openai.replayReasoning: true` on the provider entry to replay retained assistant thinking as `reasoning_content` alongside its visible content and tool calls.
The default is `false`; Responses, Codex and Anthropic ignore this option.
The destination provider controls replay, including for resumed history; selecting a provider without the opt-in stops replay.
Only retained reasoning is available: discarded or compacted thinking cannot be reconstructed.
Replayed reasoning increases the input context and is included in the projected wire-payload estimate.
This does not configure the server's chat template or `preserve_thinking` setting.
== Output budget


`max_tokens` (or `max_completion_tokens` for OpenAI-compatible wire) is
resolved from:

- the request/session value,
- the per-variant `maxTokens`,
- the provider `outputTokens` (auto-detected from `/v1/models` when unset,
  cached one day per provider/model),
- the model's own declared limit.

A large budget does not force the model to emit more: generation stops at the
natural endpoint (`stop`). Capping `maxTokens` mid-reasoning forces extra
rounds instead (measured: capping Q3 at 6000 made it *slower* - 521s vs
277s), so prefer an effort change to a hard cap.

== Sampling

`temperature`/`topP` are left to the provider defaults unless explicitly set
in `models[].options` / `tuning` / `providerSpecificOptions`. yca does not
force sampling values.

== Azure AI Gateway (Anthropic-compatible) reasoning

Azure AI Gateway / Azure AI Foundry can host Claude behind the Anthropic
Messages API on a `/messages` route. yca detects the anthropic wire
automatically from a base URL ending in `/messages` (or via an explicit
`api: anthropic`) and lets you configure the extended reasoning shape the
gateway understands - adaptive (or enabled) thinking plus an `output_config`
effort - through `providerSpecificOptions`:

[source,json]
----
{
  "provider": {
    "providers": [{
      "id": "azure-claude",
      "baseUrl": "https://<region>.inference.ai.azure.com/<project>/anthropic/v1/messages",
      "api": "anthropic",
      "model": "$azure-claude/claude-sonnet-5-5",
      "providerSpecificOptions": {
        "thinking": { "type": "adaptive", "display": "summarized" },
        "output_config": { "effort": "max" }
      }
    }]
  }
}
----

The `thinking`/`output_config` objects are merged verbatim into the top level
of every requests payload for that provider, mirroring the native Anthropic
extended-thinking request (`max_tokens` headroom is applied as usual). For the
modern Claude families (claude-4.7+ / claude-5.x, plus kimi/glm/minimax on the
anthropic wire) the same shape is also exposed implicitly as the `low`..`max`
adaptive tiers of the `/model` variant selector - selecting a variant is
equivalent to configuring `output_config.effort`.

Precedence: an explicitly configured reasoning shape (provider- or model-level
`providerSpecificOptions`) *fully overrides* the selected variant's
`thinking`/`output_config`. The variant extras do not leak extra sub-keys (eg.
a default `display`) into an explicitly configured object - explicit
configuration always wins verbatim.

When thinking is on, the Anthropic gateway reports the hidden reasoning spend
in `output_tokens_details.thinking_tokens`. yca surfaces it into the token
metrics, so `/metrics full` shows the thinking/visible breakdown and the
session reasoning total for the anthropic wire exactly like it does for
OpenAI `reasoning_tokens`. The thinking text itself streams live
(`thinking_delta`) so you see the chain of thought as it is produced.

== Benchmark parity with opencode (proxy capture) <a id="benchmark-parity"></a>

On 2026-10-09 we captured both tools' actual first request to
freeinference.org/v1 (same model `deepseek-v4-flash`, mitmproxy, TLS-capped):

[cols="1,2,2", options="header"]
|===
| field | opencode | yca 
| `reasoning_effort`
| absent
| absent (no implicit default; only set when `tuning.reasoningEffort` is configured)

| `store`
| `store:false` (+ `max_completion_tokens: 256000`)
| `store:false`

| `max_tokens` field
| `max_completion_tokens: 256000`
| `max_tokens: 393000`

| `temperature`/`topP`
| absent
| absent

| tools exposed
| 13 (`compress, edit, glob, grep, question, read, shell, skill, subagent, webfetch, websearch, write`)
| 20 (adds `apply_patch, ask_user, check_subagents, code_resolve, list_dir, manage_context, maven_knowledge_content, memory_write, read_symbol, write_file, write_todo`)

| visible reasoning in the stream
| 0 chars
| 0 chars (no implicit reasoning effort anywhere)
|===

Takeaways:

- yca sends *no* `reasoning_effort` by default for any model — absent means
  "provider default" (identical wire posture to opencode, which also omits it).
  Configure `tuning.reasoningEffort` only when a model genuinely benefits from
  it; there is no implicit fallback anymore, so reasoning is always an explicit
  opt-in, never a surprise.
- `store:false` is wired from the core request builder (opencode parity), so
  requests are marked not-to-retain server-side.
- opencode's wire has fewer tool schemas (13 vs 20 in full); each schema rides
  every request, so a leaner tool allow-list (`yca.tools.builtin.enabledTools`)
  is a per-call token saving for any agent.
- `max_completion_tokens` vs `max_tokens` is a naming difference on the same
  wire family; both are "headroom", not forced output.

=== Measured parity (2026-10-09, N=3 median, deepseek-v4-flash)

yca was run with reasoning absent + `store:false` + a 7-tool allow-list
(`bash, read_file, write_file, edit_file, glob, grep, list_dir`) + the log-noise
output filter + the configurable bash output cap. opencode ran on the same
prompts, model and repository tasks (verified = the produced project passes its
`mvn test`).

With the lean wire posture (no reasoning, `store:false`, fewer tool schemas,
log-noise filter and the bash cap) yca completes all three tasks *faster* than
opencode and with roughly *half* the context ceiling (max context 0.55-0.62x,
accumulated context ~0.5x) at the same task-success rate. The largest relative
win is on the multi-file Q3, which is where uncontrolled framework-log noise and
huge tool outputs otherwise inflate the transcript.
