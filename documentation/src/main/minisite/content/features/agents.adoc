`yca.agents` defines named agents. Each is mostly a prompt whose instructions
are injected on top of the base system prompt (rules, tools, environment,
project context, skills and memory stay untouched).

An agent is selected on `run` with `--agent <name>`, in the TUI with
`/agent <name>` (persistent until `/new`), or per-turn by prefixing a prompt
with `@<name> `.

== Defining agents

`yca.agents` is a list of named profiles. The `prompt` is inline text, or a file
path whose content is loaded when it expands to an existing regular file (for
example `prompt=~/.yupiik/coding-agent/agents/reviewer.md`). The optional `tools`
list restricts the profile to those tool names; omitting it leaves the normal
session and permission rules in force. Set `description` to a short purpose and
delegation hint for catalog discovery; keep detailed instructions in `prompt`.
An optional `model` uses the same object as background model tuning: `name` is
the model id or `$provider/model` route, and the remaining fields tune requests
made by that agent. When absent, the agent uses the current contextual model.

.Example configuration.json
[source,json]
----
{
  "agents": [
    { "name": "reviewer", "description": "Reviews changes for bugs and regressions without editing files.", "prompt": "~/.yupiik/coding-agent/agents/reviewer.md", "tools": ["read", "glob", "grep"], "model": { "name": "$local/qwen3-coder", "reasoningEffort": "high" } },
    { "name": "tester", "prompt": "You are a meticulous test author. Prefer table-driven tests and always run them." }
  ]
}
----

== Sub-agent model routing

A sub-agent spawned with `spawn_subagent model=<reference>` runs on the model
(and provider) named by the reference. `$<provider>/<model>` routes explicitly;
a bare name is pinned to whichever configured provider declares it, falling
back to the parent's provider. Model choice precedence is: explicit spawn
`model`, selected profile's `model.name`, provider `defaultSubagentModel`, then
the inherited contextual model. A configured profile model also applies when
that profile is selected for a normal run. Profile model configuration is
temporary to that run and does not replace the session's contextual selection.

Resolution reuses the same `$provider/model` machinery as background model
references, so specialists can use a cheaper model or a different provider.
The resolved model of a running/recently-completed sub-agent is surfaced in the
`/subagents` overlay when a reference was requested.

== Discovering profiles and models

The `list_subagent_options` tool searches agent profiles and configured model
routes on demand. It accepts `kind` (`agents`, `models`, or `all`), a substring
`query`, a provider filter, and pagination (`offset` and `limit`). The tool
schema contains no profile or model list; results are returned only when called,
with 20 entries by default and a hard maximum of 50 per page. Profile prompts
are never returned, and descriptions are capped at 300 characters. Model
results include configured provider model ids and provider defaults; the tool
does not query live provider catalogs.

Optional catalog and routing ceilings are configured under
`yca.tools.spawnSubagent`:

[source,json]
----
{
  "tools": {
    "spawnSubagent": {
      "allowedAgents": ["reviewer", "tester"],
      "allowedProviders": ["default", "local"],
      "allowedModels": ["$local/qwen3-coder", "gpt-5-mini"]
    }
  }
}
----

Empty or omitted allowlists leave that choice unrestricted. Restrictions filter
catalog results and are checked again when a spawn request is made.

The resolved model of a running/recently-completed sub-agent is surfaced in the
`/subagents` overlay (list rows and the detail transcript) when a reference was
requested.

== Sub-agent run limits and tools

`spawn_subagent` accepts an optional `agent` profile, a `tools` allowlist, and
`max_turns`. The requested tools are intersected with the profile's tool list
when both are present, and are enforced both in the child model's tool schema
and again before tool execution. An empty `tools` list allows no tools. Unknown
profile names or unavailable requested tools fail the child run. Sub-agents use
separate permission grants; their approval prompts still appear in the parent
session. Parent permission restrictions remain in force.

`max_turns` counts model round-trips. A positive per-spawn value sets an upper
bound; a non-positive or omitted `max_turns` disables the per-spawn override so
the configured `yca.subagents.maxIterations` and applicable provider/model
iteration cap apply. The effective limit is the lowest of the per-spawn value,
configured `yca.subagents.maxIterations`, and applicable provider/model
iteration cap. Nested sub-agents are disabled.

Sub-agent admission enforces two independent limits. `yca.subagents.maxConcurrent`
bounds how many sub-agents one session may keep in flight. Independently, each
provider's `maxConcurrent` (or the global `yca.llm.maxConcurrent` fallback)
reserves one slot for the main session: a provider with `maxConcurrent=1` cannot
run sub-agents at all, and a provider with `N > 1` runs at most `N-1` concurrent
sub-agents process-wide. When a spawn is refused, `spawn_subagent` returns a hint
naming the limiting factor (the session cap or the target provider's cap).
