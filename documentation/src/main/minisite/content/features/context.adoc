= Context management
:minisite-breadcrumb: Home[index.html] > Features > Context management
:minisite-nav-prev-link: mcp.html
:minisite-nav-prev-label: MCP support
:minisite-nav-next-link: compaction.html
:minisite-nav-next-label: Compaction and compression

As a conversation grows, context usage is tracked with live gauges.
When usage crosses configured thresholds, yca prunes or compacts the
conversation to stay within the active model's window.

NOTE: since 1.0.x the default context management is the two-layer model
described in xref:features/compaction.adoc[Compaction and compression]: core
compaction triggers near the model window (window minus max(15%, 16k) tokens)
while a model-invoked `compress` tool keeps the working context small with
absolute nudges at 50k/100k tokens. The legacy percentage bands below apply to
the opt-in pruning layer (`yca.pruning.enabled=true`, off by default) and to
compaction when a legacy percent override is configured
(`yca.compaction.thresholdPercent` > 0).

The default thresholds carve the usable window into bands, so the model always
sees its usage relative to the automatic actions that will fire:

[mermaid]
....
graph LR
    W["Usable window\n(context window - output headroom)"]
    subgraph Bands
        N["0 - 55%\nnudge band"] --> P["55 - 65%\nsoft nudge"]
        P --> R["65 - 80%\nprune fires"]
        R --> C["80% +\ncompaction fires / overflow"]
    end
    W --> Bands
    C -->|compact| S["Summary + verbatim tail"]
    S --> W
....

== Usage tracking: real tokens first

Threshold decisions are anchored on real usage whenever the provider reports
it: the last observed `prompt_tokens` value is used as an anchor and the
messages appended since that call are estimated on top.
The appended estimate is calibrated by the ratio between the anchor and the
estimate of the anchored request, clamped to `[0.5, 2.0]`, so a conservative
heuristic never turns into an over-aggressive trigger once real data exists.
Before the first response of a session (no anchor yet), the raw heuristic
estimate is used.

In the TUI sidebar the estimate is labeled `context ~` and, when the provider
has reported usage at least once, a `last real` row underneath shows the exact
provider-billed `prompt_tokens` of the last anchored request (the real base the
estimate is built on). The absence of that row means no anchor exists yet, so the
`~` value is heuristic only. `/context llm-payload` prints the same contract as
text: the footprint estimate, the last real prompt tokens and the calibration
ratio, plus whether the context window came from an explicit value or the
auto-detected baseline.

All percentages are computed against the _usable_ window: the configured or auto-detected context window minus the output budget the model declares, so prompts leave room for completions.
The declared output budget comes from the per-model `behavior.outputTokens`, the provider `outputTokens`, or the detected `/v1/models` `max_tokens` / `top_provider.max_completion_tokens`: a 262144 window declaring 32768 completion tokens leaves a usable window of 229376.
When no output budget is declared, or when it is not smaller than the window (hence cannot be honoured), a conservative `min(20000, window / 4)` headroom is reserved instead.

=== Context window resolution

The context window used by the gauges, pruning and compaction resolves in this
order:

1. a per-model override: `yca.provider.providers[i].models[j].contextWindow`
   (an `int` in tokens, `0` or negative = unset) - wins over everything for the
   matched model (exact id first, then the configured model id as a substring);
2. the provider value `yca.provider.providers[i].contextWindow` (an `int` in
   tokens, `0` or negative = unset);
3. a value auto-detected once a day from the provider `/v1/models` vendor
   extensions (`context_window`, `model_context_window`, `context_length`,
   `top_provider.context_length`, `max_model_len`, `max_input_tokens`,
   llama.cpp `meta.n_ctx`, or `meta.n_ctx_train` when smaller), cached per
   provider and model under the storage home;
4. a conservative `32000`-token baseline when nothing is known (guessing too
   high on a small-window model would turn every request into a context-window
   overflow).

Detected and configured values are totals (prompt + completion combined) in
_tokens_, and the output budget declared next to them (configured
`outputTokens`, or detected `max_tokens`/`top_provider.max_completion_tokens`)
is reserved from that total to compute the usable window.
The per-model and provider values count as explicit configuration: an
overflow-triggered auto-shrink never persists a halved window for a model or
provider carrying an explicit value, it only affects the auto-detected cache.

This lets one base URL serve models of very different windows (e.g. a 32k qwen
and a 1M deepseek): give each model its own `contextWindow` entry and the
pruning/compaction thresholds follow the active model.

== Pruning: cheap local clearing

Pruning (default trigger: 65% of the usable window) never calls the LLM.
It walks old tool results backwards and reduces them in two rungs: verbose
outputs are first spliced to their head and tail
(`yca.pruning.shrinkOutputChars`, default 2000, 0 disables the shrink pass),
keeping a self-describing `[... N chars elided ...]` marker in place of the
dropped middle; only when the reclaimed volume alone is not enough are the
remaining outputs replaced with `[old tool result cleared]`, still keeping the
assistant tool call itself so the message pairing stays valid.

The recent side of the conversation is protected by both rungs: at least
`yca.pruning.keepRecent` messages (a floor), the `yca.pruning.protectTurns`
most recent turns, and `yca.pruning.protectRecentTokens` estimated tokens of
the newest tool outputs.
Pruning only rewrites anything when the volume it would reclaim exceeds
`yca.pruning.minPruneTokens`, which avoids churn on small gains.
When nothing qualifies, pruning is a no-op.

Because pruning is local, `model.prune` is no longer used (the key is
accepted but ignored).

Alongside the volume-based rungs above, three zero-LLM strategies shrink
specific history without calling the summarizer (all report the `CLEARED`
outcome label, see xref:#outcome-labels[Outcome labels below]):

- `yca.pruning.deduplicateToolCalls` (default `true`) drops identical tool
  calls (same tool, same normalized arguments), keeping only the latest.
- `yca.pruning.supersedeOverwrittenWrites` (default `false`) replaces the
  input of write operations (`write_file`/`edit_file`/`apply_patch`) that a
  later read of the same file overwrote.
- `yca.pruning.purgeFailedToolInputs` (default `true`) removes the (often
  large) input of failed tool calls after `yca.pruning.purgeFailedToolInputsTurns`
  turns (default `4`), keeping the error message.
- `yca.pruning.purgeDeliveredSubagents` (default `true`) truncates delivered
  sub-agent `<subagent>` blocks to their sessionID/state/description line after
  `yca.pruning.purgeDeliveredSubagentsTurns` turns (default `10`), keeping the
  last two deliveries verbatim so the model still sees "what just finished".

State-bearing tools (`write_file`, `edit_file`, `apply_patch`, `todo_*`,
`memory_write`) are never deduplicated, superseded or input-purged.

== Compaction: structured summary plus verbatim tail

Compaction (default trigger: 80% of the usable window, or a provider context
overflow with retry) summarizes the old part of the conversation with the LLM
and keeps a verbatim tail.

The summarizer model resolves per background call: the effective provider's
`backgroundModelOverrides.compact` wins when set, then the global
`model.compact`, then the session's own provider/model. The same resolution
applies to the memory write path (`backgroundModelOverrides.memory` vs
`model.memory`) and to pruning (`backgroundModelOverrides.prune` vs
`model.prune`).

The summary follows a fixed structure - `## Objective`, `## Important Details`,
`## Work State` (Completed / Active / Blocked), `## Next Move` and
`## Relevant Files` - and preserves exact file paths, commands and errors.
When the context was already compacted before, the previous summary is fed
back as `<prior-summary>` and updated in place instead of being re-summarized
from scratch.

The kept tail is token-budgeted (`yca.compaction.tail.budgetTokens`, 0 = auto:
25% of the usable window clamped to `[2000, 15000]`) and aligned on
conversation turns: the boundary never splits an assistant tool call from its
tool results, and `yca.pruning.keepRecent` acts as a floor on the tail size.
The most recent user message is guaranteed to survive: it is either inside the
tail or replayed verbatim after the summary.

Tool call arguments are capped before the summarizer input is built
(`yca.compaction.tail.toolArgumentsCapChars`, default `800`, `0` = keep verbatim):
a single bash or JSON argument blob can otherwise dominate the input and
multiply the rolling-summary LLM calls for no digest value. The exact payload
stays available in the verbatim tail for recent calls.

The summarizer input is chunked adaptively to the compact model's window. By
default (`yca.compaction.summarizer.chunkChars`, `0` = auto) each summarizer
call covers a quarter of the compact model's usable window in characters
(~4 chars/token), floored at `yca.compaction.summarizer.minChunkChars`
(default `12000`, the legacy fixed 12k chunk): most compact models therefore
run in a *single* LLM call instead of ten small ones. The rolling digest kept
across chunks is capped by `yca.compaction.summarizer.digestChars` (default
`0` = half the chunk cap), so a merge call always stays inside the window.

When a summarizer call is rejected because the input exceeds the model's real
context window (a size-caused failure, not a transient error), the chunk cap
is *halved* down to the configured floor and compaction restarts from the
previous summary (the partial digest is discarded). The restart is bounded:
each halving bisects the space, so a 1M-token model degrades through at most
~6 rounds before giving up. Non-size failures (auth, 5xx, timeouts) keep the
per-call retry/backoff and never trigger a halving. Both the halving restarts
and the final degradation are surfaced as warnings so the user sees that
compaction took the slower path (and with which chunk size).

If the summarizer eventually fails, compaction degrades to a deterministic
local truncation (`yca.pruning.toolOutputMaxChars` caps old message content)
and reports the fallback honestly instead of a fake success. Old tail
messages that still overflow after compaction are spliced to their head and
tail (`yca.compaction.tail.overflowSpliceChars`, default `500`).

Automatic compaction uses a trigger and a separate provider input limit. The
normal compaction keeps its configured recent tail; if the resulting prompt is
still above the trigger, the agent makes at most one tighter forced-compaction
pass during that turn. Tool-schema tokens are included in this trigger check.
If the prompt remains above the trigger but is still within the provider input
limit, the agent warns once and continues rather than ending the turn after a
fixed number of compactions. A provider-reported context overflow still uses
the separate bounded overflow-retry path.

=== Trigger safety headroom

The effective compaction trigger is never allowed to sit too close to the hard
window: `yca.compaction.buffer.safetyPercent` (default `90`) caps the trigger
at that percentage of the usable window, so a large configured output reserve
cannot push the trigger (and hence the "safe" headroom the gate targets) into
the last few percent where an over-budget completion would overflow.
A per-provider override exists under
`yca.provider.providers[i].compaction.buffer.safetyPercent` (null/absent =
inherit global).
The safety cap never equals the usable window at `100`: the trigger keeps a
buffer over the hard limit.

=== The compaction gate

When a turn's checkpoint leaves the context over the trigger even after the
automatic compact and the tighter forced pass, the agent runs the _compaction
gate_: a bounded sequence of recovery attempts before the request is sent, so
it never sends a prompt above the trigger and never blocks the turn forever on
a non-compactable context.

Each gate attempt first runs an LLM-backed forced-recovery compaction (the
normal tail budget halved), then - if that produced no progress - an LLM-free
local spill of pre-digest tool outputs.
Between attempts the gate backs off (bounded, interruptible), and the whole
sequence is capped by two budgets:

- `yca.compaction.gate.maxAttempts` (default `12`): how many recovery passes the
  gate may run;
- `yca.compaction.gate.maxDurationMs` (default `300000`): the wall-clock budget
  of the whole gate.

Both are overridable per provider
(`yca.provider.providers[i].compaction.gate.maxAttempts` /
`gate.maxDurationMs`, null/absent = inherit global), so a flakier provider can
raise its own gate ceiling without affecting the others.

The gate escalates - a pinned `Compaction gate:` error and continuing to
monitor the hard limit - instead of looping forever when:

- a recovery pass reclaims nothing at all;
- two consecutive passes each reclaim less than `5%` of the pre-pass context
  (the context is not compactable further with the current strategy);
- the attempt or wall-clock budget is exhausted while still over the trigger.

Escalation never blocks the request: the turn proceeds and watches the
provider hard limit. A user can always force guaranteed progress with
`/compact urgent`, which falls back to destructive local truncation when the
summarizer fails.
Pressing Esc mid-gate aborts the recovery loop without escalating.

=== Compaction retries: one authority

The compaction summarizer owns its retry loop: it calls the chat client with
the `COOPERATIVE` retry mode, which asks the client-side resilience wrapper to
skip its own internal retries (the conversation loop keeps its own
`yca.llm.retriesMaxAttempts` behavior unchanged).
There is therefore exactly one retry authority per call, and the compaction
budget is controlled by `yca.compaction.retriesMaxAttempts` (default `3`),
overridable per provider
(`yca.provider.providers[i].compaction.retriesMaxAttempts`), then flattened to
`yca.llm.retriesMaxAttempts` and floored at `1`.
The backoff between compaction retries uses the same
`yca.llm.retriesBaseDelayMs` (and multiplier) as the conversation retries.

For a flaky provider, the compaction summarizer can be given a higher ceiling
than the conversation without slowing replies on the happy path:

[source,text]
----
yca.provider.providers.0.compaction.retriesMaxAttempts=6
yca.llm.retriesBaseDelayMs=3000
yca.provider.providers.0.rateLimitRequestsPerMinute=20
yca.provider.providers.0.compaction.gate.maxAttempts=20
----

The cooperative mode still honors the semaphore and rate-limit throttles, so a
slow provider is never hammered by the summarizer retries.

=== Digest-only contexts and repeated /compact

When almost the whole history is a previous `<compacted-context>` digest
followed by a long tool-churn turn, a normal `/compact` finds nothing real to
summarize against and would keep returning `NONE`.
The digest-only rescue cuts at the first safe tool-call/result boundary and
folds the new summary into the previous digest, so repeated manual compacts
actually reclaim the churn instead of spinning.
The `compress` tool reports the same situation explicitly: when the only user
message left is the compaction digest, its skipped-range guidance points at
`/compact` ("run /compact to reduce the tool round") instead of asking for
more small disjoint ranges that cannot be anchored.

=== Speculative compaction

`yca.compaction.speculative.policy=concurrent` (see
xref:features/compaction.adoc[Compaction and compression]) starts a background
summary as soon as usage crosses `yca.compaction.speculative.startPercent`, so
the next turn often adopts a ready candidate instead of stalling on a
synchronous compact.
The gate is the safety net underneath: a concurrent candidate that is too
small, or that fails to land below the trigger, still goes through the bounded
recovery sequence above rather than limping above the trigger.

[#outcome-labels]
Every in-loop prune/compact records _how_ the context was reduced as an
outcome label (the `mode` field of the `AgentEvent.Compacted` event and of
`CompactionDoneEvent`):

- `NONE` - nothing needed to be (or could be) done.
- `SUMMARY` - the LLM summarizer produced the reduced context.
- `TRUNCATE` - the summarizer failed and a deterministic local truncation ran.
- `CLEARED` - old tool outputs were cleared locally (no LLM call).
- `SHRUNK` - old verbose tool outputs were spliced locally, keeping their head
  and tail (no LLM call).

The zero-LLM strategies that run alongside pruning (`yca.pruning.*`) - dedup
of identical tool calls, superseding of overwritten writes and purging of
failed-tool inputs - always report `CLEARED`, since none of them invokes the
summarizer.

Every reduction of the same checkpoint is delivered as a single
`AgentEvent.Compacted` (and `CompactionDoneEvent`) whose `kinds` list carries
the applied strategies in execution order, e.g. `["dedup", "prune"]` when
identical tool calls were removed and old tool outputs were cleared together.

The digest is delivered to the model as a user message wrapped in
`<compacted-context>` followed by explicit guidance: it must treat the
compacted context as _historical state_ and must not reload, reconstruct or
repeat actions already described in it - only call tools that serve the
current task. The system prompt carries the same rule as a durable static
constraint, so sessions compacted before this guidance existed are covered
too.

== Persistence

Every in-loop pruning or compaction is written back to the session store
immediately (same as `/compact`), so the next turn never re-summarizes an
already-compacted context.

[#inspecting-the-context]
== Inspecting the context

The `/context` command dumps the context, and it takes a mode plus an optional
file path.
Every mode writes to the transcript when no path is given and to that file when
one is, so a 100k context lands on disk instead of in the scrollback.

[cols="1,2",opts=headers]
|===
|Mode
|What it dumps

|`transcript`
|The persisted session: the system prompt followed by one line per stored message.
The default, so `/context` and `/context out.txt` keep working unchanged.

|`llm-payload`
|The exact last request sent to the provider: every message with its full content,
the assistant tool calls with their raw arguments, and the wire tool schemas.
This is what the model really received, which the transcript is not.
The tools section header summarizes the aggregate estimated token cost of all
the wire schemas (`~N tokens estimated for all the tool schemas`); each per-tool
block carries its own estimate too (`**parameters** (~N tokens estimated)`).

|`next-request`
|The request the next round would carry, rebuilt from the persisted session and the
current system prompt without calling the provider.

|`compact`, `prune`
|The context operations, as above.
They take no path.
|===

`llm-payload` and `next-request` differ by one thing only: the first is a
snapshot taken right before the call, the second is a reconstruction.
A reconstruction cannot be the history, because the volatile session state
depends on live values - the context usage line, the nudge band, the memory
version captured at turn start - that were never persisted.
That is why the persisted transcript is not the payload either: the store drops
the leading system message and the volatile tails, so the transcript is a
subset of what the model sees.
When a session sent no request yet, `llm-payload` says so instead of guessing;
run a turn first, or use `transcript`.

[#soft-context-usage-nudge]
== Soft context-usage nudge

The nudge is a soft, LLM-free early warning delivered through the volatile
session state (`<session-state>`), well before pruning and compaction fire.
It invites the model to wrap the current step up, or to manage its own context
via the `manage_context` tool.
By default the nudge is enabled and tuned to be quiet on small windows and
informative on large ones.
It complements, and never replaces, the automatic pipelines: it only emits
text into the session-state tail, so the byte-stable conversation prefix, the
prompt cache and the automatic pruning and compaction are untouched.

A nudge is emitted only when all three of these conditions hold:

* the estimated context reaches `yca.pruning.nudgeThresholdPercent` (default
  `55`) percent of the usable window - below the prune threshold (`65`) and
  the compaction threshold (`80`), so the model hears the warning one full
  band before any automatic action;
* at least `yca.pruning.nudgeIterationThreshold` (default `15`) iterations ran
  since the last user message, so short turns stay silent;
* the estimated context is at least the absolute floor - see <<small-windows>>
  below.

Setting `nudgeThresholdPercent` to `0` disables the nudge entirely (the
system-prompt guidance and the per-tail usage line are then also dropped).

Regardless of the nudge, every session-state tail reports the live usage
number:

[source,text]
----
Context usage: ~61% of the usable window (prune at 65%, compaction at 80%).
----

The model therefore always has its real usage and the decision thresholds in
front of it, and the `<nudge>` block only appears when it should act on them.

=== Escalation

The nudge wording escalates with usage:

* between `nudgeThresholdPercent` and the prune threshold, the soft
  `yca.pruning.nudgeTemplate` is used (`Context is at ~%USAGE%% of the usable
  window. Prefer wrapping this step up, or compact soon.` by default);
* once usage reaches or exceeds the prune threshold
  (`yca.pruning.thresholdPercent`), the urgent
  `yca.pruning.nudgeUrgentTemplate` is used (`Context is at ~%USAGE%% and
  above the prune threshold (%PRUNE%%). Do not start new work - %ACTIONS% now
  to avoid the hard compaction wall.` by default).

Both templates support the `%USAGE%`, `%PRUNE%`, `%COMPACT%` and `%ACTIONS%`
placeholders.
`%ACTIONS%` renders the concrete next step and only ever mentions
`manage_context` when the tool is actually exposed
(`yca.tools.manageContext.enabled`); otherwise it falls back to a neutral
"interrupt with a short summary of the remaining steps" wording.

=== System prompt guidance

When the nudge is enabled and `manage_context` is exposed, the system prompt
carries a durable rule telling the model that the session state reports the
current context usage and thresholds, and that it should proactively call
`manage_context` (`action=prune` or `action=compact`) rather than waiting for
the hard limit.
The rule lives in the byte-stable system prompt, so it applies from the first
turn even though the tail numbers are volatile.

=== Small windows

[#small-windows]
The absolute floor prevents noisy nudging on small contexts: the nudge is
suppressed while the estimated context is below
`min(0.9 * usable window, yca.pruning.nudgeMinTokens)`.
With the default `nudgeMinTokens` of `64000`, a small provider (for example a
`32k` window, about `24k` usable) never gets percentage nudges all the time -
the floor sits at about `90%` of its window, so at most the urgent wording can
fire right before compaction, which is cheap anyway on such models.
On a large window the floor caps at `64000` tokens (~44% of a `128k` window's
usable space), well below the `55` threshold, so the nudge keeps its full
lead time where compaction is expensive.
Set `nudgeMinTokens` to `0` to disable the floor.

|`nudgeMinTokens`

== The manage_context tool

When `yca.tools.manageContext.enabled` is set (the default), the model gets a
`manage_context` tool so it can manage its own context:

[cols="1,2",opts=headers]
|===
|Action
|Behavior

|`status`
|Reports the current usage (effective tokens, window, percent, thresholds).

|`compact`
|Requests a compaction, applied after the current tool round.

|`prune`
|Requests a tool-output pruning, applied after the current tool round.
|===

`compact` and `prune` accept an optional `focus` hint folded into the summary
prompt and a `keep_last` floor override.
Guardrails: a request is refused below 30% usage, and at most one
model-initiated operation runs per turn.
See xref:../configuration.adoc[Configuration] for the `yca.pruning.*` and
`yca.compaction.*` options.

== Context-management philosophy: deterministic, not model-driven

Some coding agents (opencode-style) teach the model to call a `compress` tool
at semantic phase boundaries: "data collected", "implementation validated",
"before writing the final report".
The model decides *when* and *what* to summarize, and the intervention is
visible in the transcript as meta-narration.

yca made the opposite bet: the *decision* to prune or compact is
deterministic.
It fires on measured usage against thresholds (65% / 80% of the usable window
by default), anchored on the last real provider `prompt_tokens` when
available.
The model never decides *when*; it only influences *what* to preserve, through
the `manage_context` tool (`focus` and `keep_last`) and the soft nudge that
invites it to wrap up early.

This trade-off favors predictability over adaptability:

* each model-initiated compaction is an extra LLM call, so an aggressive
  phase-compressing model pays tokens for summaries the window does not need;
* the deterministic pipes always run on the same thresholds, so behavior does
  not depend on the model's mood or its sampling luck on a given turn;
* the transcript stays clean: no "let me compress this phase" interjections,
  compaction appears as a silent event;
* fidelity is protected mechanically, not by a summary written at a lucky
  moment: the verbatim tail, the `keepRecent` floor and the guaranteed
  survival of the last user message all survive compaction regardless of the
  model.

NOTE: the two approaches are not mutually exclusive.
yca still lets the model drive the *content* of a compaction, it just never
lets the model drive its *timing*.

== Opting into model-driven compression

You can get opencode-style phase compression without changing the engine, by
teaching the model to compact at natural phase boundaries through
configuration only.
The deterministic pipes stay as a safety net underneath.

Three configuration levers combine to enable it:

. Expose the self-service path: `yca.tools.manageContext.enabled=true` (the
  default) gives the model the `manage_context` tool.
. Keep the durable guidance: `yca.pruning.nudgeThresholdPercent > 0` (the
  default `55`) is what injects the system-prompt rule telling the model to
  proactively call `manage_context` instead of waiting for the hard limit.
. Teach phase boundaries: add a custom agent
  (xref:features/agents.adoc[Custom agents]) or a project/global `AGENTS.md`
  rule whose prompt instructs the model to compact when a phase completes.

.Example agent prompt enabling phase-boundary compaction
[source,text]
----
Compress phase boundaries: when a task phase completes (data collected,
implementation validated) call manage_context with action=compact and a focus
that summarizes the phase (decisions, results, next steps) before starting the
next phase or writing the final answer.
----

You can also tune the nudge wording with
`yca.pruning.nudgeTemplate` and `yca.pruning.nudgeUrgentTemplate`
(see <<soft-context-usage-nudge>>) to invite a compact at wrap-up instead of
merely wrapping up.
The `%ACTIONS%` placeholder already renders a `manage_context` suggestion when
the tool is exposed (see <<soft-context-usage-nudge>>).
