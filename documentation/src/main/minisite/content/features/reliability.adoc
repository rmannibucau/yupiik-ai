Model calls are protected against transient failures: yca applies rate
limiting, automatic retries and concurrency limits so bursts and API hiccups do
not break a session.

== Concurrency limiting

A provider account (or API key) only serves a bounded number of concurrent
requests; beyond it the provider answers `429 concurrency_limit_exceeded` and
burns the caller's quota on retries.

yca caps the in-flight requests of a provider with a concurrency gate: one
permit per request attempt, returned as soon as the answer (or the failure) is
in - never held during a retry backoff, so a retrying caller does not keep a
slot the other callers of the budget need.

=== Per-process budget (default)

By default each yca process owns one in-memory gate per provider, with a strict
FIFO admission: waiters are served in arrival order and a newcomer never barges
a slot a queued caller was about to get. The gate is shared by every client of
the provider in the process - the main conversations and the `/btw` side
questions - so a side question cannot exceed the budget.

The cap is the per-provider `maxConcurrent` when it is strictly positive,
otherwise `yca.llm.maxConcurrent`.
A provider `maxConcurrent` of `0` defers to `yca.llm.maxConcurrent`.
With neither value set, shared gates start unbounded and a provider-announced limit narrows the gate for all clients.

When no limit is configured, the first `429 concurrency_limit_exceeded` response creates a gate bounded by the announced `"limit": N`.
Shared provider gates retain learned narrowing for their lifetime so one client's cooldown cannot widen another client's budget.
Private library gates relax back to the configured cap (or to no bound) after `concurrencyAdaptationMs`.

An admission is bounded: a request which cannot get a slot within
`yca.llm.concurrencyAcquireTimeoutMs` (default 5 minutes) fails with a
`ConcurrencySlotTimeoutException` instead of hanging forever on a saturated
budget - another process holding every lease, or a suspended one. That failure
is deliberately its own type: a saturated budget is not a flaky transport read,
so it is not retried (retrying would multiply the admission deadline by the
attempt count while the provider is asking yca to slow down).

The uncontended admission runs on the caller's thread; only a wait is moved to
a virtual thread, so a slot holder never starts the next request from its own
thread.

=== Account-wide budget (file leases)

Several yca sessions on the same machine talk to the same account, so
per-process gates multiply the concurrency the provider actually sees: three
sessions at `maxConcurrent = 2` issue six concurrent requests against a budget
of two.

When a provider opts into `capabilities.concurrency.useFileLock` _and_ a
strictly positive bound is configured (the provider's `maxConcurrent` or the
global `yca.llm.maxConcurrent`), the budget of that provider is shared across
every yca process of the machine through file leases under the storage home
(`llm-concurrency/<providerId>`): each grant holds an exclusive OS record lock
on one `slot-N.lock` file, so two processes cannot hold the same slot. Record
locks are released by the kernel when their holder dies, so a killed or crashed
session never leaves a slot stranded.

Record locks are reliable on a local POSIX filesystem only. On NFS/CIFS they
may be ignored or coalesced by the client, so the leases only coordinate the
processes of one machine sharing one storage home - and when the filesystem
refuses them, the gate degrades to a per-process budget (logged once as a
warning, also exposed through the gate) instead of failing requests.

The slot files are never deleted (a recreated file would be a different lock
domain, hence a slot which looks free while it is still leased). The
`llm-concurrency` directory is safe to remove while no yca process runs.

A capacity learned from a `429` is persisted in a sibling `capacity` file with a 24-hour time-to-live, so a restart seeds the gate with the last known limit instead of burning another `429` to rediscover it.
Concurrent writers retain the smallest unexpired learned value and publish it atomically.
Only a learned value is persisted; a local capacity update does not erase what a peer learned.

Reconciliation is best effort: a `capacity` file written after a process started is not re-read by that process for admission.
Use the same provider id, storage home and configured bound in all processes that share an account.
Different ids do not coordinate even when they use the same API key, and unsafe directory ids are mapped to a SHA-256 directory name.
A learned lower bound is not an instantaneous machine-wide guarantee: peers may still use their previous bound and existing requests are never preempted.

=== Bounded waits and cancellation

Queued callers observe the wait through the same pause notifications as
throttling and backoffs, and an abandoned turn (interrupt, tab close) gives up
its place in the queue instead of parking for nothing.

== Turn loop guards

A single turn can run many LLM round-trips. Iteration bounds (the per-window
cap, the exploration-plateau guard and the persisted stop notices) follow a
per-model / per-provider / global cascade and are covered in detail in
xref:features/iteration-guards.adoc[Iteration guards].

== Spawned processes

Every subprocess yca starts (the `bash` tool, stdio MCP servers, the Maven
`dependency:list` resolver, clipboard helpers) is tracked by the shared
`ProcessService` so a running command can always be stopped as a _tree_ and no
subprocess outlives the JVM:

* Cancelling a turn, a tool call or a bash timeout disposes the whole process
  tree (`ProcessHandle.descendants()` first, then the leader), so orphaned
  foreground children (`mvn`, `npm`, a `sleep … & wait` script) are reaped too,
  not just the direct shell.
* Closing is two-phase: at shutdown every tracked tree is killed first, then all
  of them are awaited with a single shared deadline (`onExit()` +
  `CompletableFuture.allOf`), so the total wait is the slowest single reap, not
  a per-process sum.
* The disposal runs on the container `@Destroy`, i.e. at the end of every
  command (fusion's `CliAwaiter`) and, when fusion's launcher hook is enabled
  (`fusion.launcher.useHook=true`), on raw JVM exit too - so a Ctrl-C
  force-exit or `SIGTERM` still reaps tracked processes. With the hook off,
  graceful exits (normal command return, the cooperative Ctrl-C path) still run
  the container close; a hard `kill -9` cannot run any code, so nothing can
  clean up in that case.
