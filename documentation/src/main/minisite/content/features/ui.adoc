= Interactive UI and headless mode
:minisite-breadcrumb: Home[index.html] > Features > Interactive UI and headless mode
:minisite-nav-prev-link: sandboxes.html

yca can be driven through two interactive frontends or in a single-shot headless
mode.

The xref:../cli/tui.adoc[`tui`] command opens a full-screen interface: markdown
transcript, token gauges, a streaming thinking view, approval modals, todos and
an editable plan (`/editplan`).

The xref:../cli/cli.adoc[`cli`] command is a plain-terminal REPL with the same
agent underneath: streamed ANSI-colored output, sessions, todos, approval and
feedback gates and the same slash commands.

For automation, the xref:../cli/run.adoc[`run`] command executes a single
headless prompt and prints the result on stdout. It exits non-zero on failure,
making it easy to call from scripts and CI.

== Account usage quota

When the current provider advertises the Codex usage capability
(`capabilities.codex.enableUsage`, see xref:../configuration.adoc[Configuration]),
the TUI and web sidebars show a *Usage* section under the context gauge: the plan
type, the used percentage of the primary rate-limit window and a progress bar
(number + %, refreshed at most every 5 minutes, hidden entirely when the current
provider does not expose usage). The data comes from the provider's Codex usage
endpoint, fetched in yca (the token never leaves the process); the web frontend
only consumes the broadcast usage event.

The `/usage` slash command forces a refresh and prints the full quota (plan,
rate-limit windows with their reset times, credits) as a table.

== Speaker labels

The transcript headers (the `▌` line opening every user and assistant turn) are
configurable through `yca.labels`:

[source,json]
----
"labels": {
  "userTemplate": "[{{formatDate \"HH:mm:ss\"}}] {{systemProperty \"user.name\" \"You\"}}",      <1>
  "assistantTemplate": "[{{formatDate \"HH:mm:ss\"}}] {{model.provider}}::{{model.name}}"  <2>
}
----
<.> Header template rendered for user turns.
<.> Header template rendered for assistant turns.

NOTE: shown as a fragment of `yca.labels` - the surrounding `yca` object is omitted.

Both are Handlebars templates. The context keys are `userName`
(`System.getProperty("user.name")`, missing values are skipped), `modelName`,
`model` (`name`, `provider`), `provider`, `agent` (the active custom agent or
empty), `mode` (`plan`/`build`), `sessionId` and `configuration` (the whole yca
configuration map). The `systemProperty` helper reads a system property with an
optional default: 1 argument ({`{{systemProperty "user.name"}}`}) renders the
value or nothing when the key is absent, 2 arguments
(`{{systemProperty "user.name" "You"}}`) add the fallback. A template rendering
blank falls back to `You`/`Assistant`.

The `formatDate` helper renders the current time from the injected clock:
`{{formatDate}}` uses `HH:mm:ss`, `{{formatDate "yyyy-MM-dd HH:mm:ss"}}` accepts
any `java.time` pattern; remove it from the template to disable the timestamp.

[IMPORTANT]
====
Speaker labels are strictly a UI feature: they only decorate the rendered
transcript headers. The LLM conversation always keeps its hardcoded
`user`/`assistant` roles (the session store and the wire payload stay
label-free), the compaction summaries keep their `[Assistant]:` /
`[Assistant tool call]:` prefixes and subagents keep `Assistant: ` regardless of
these templates. Changing the active model only changes what headers display,
never what the model receives.

The producing identity (provider, effective model, agent) is captured on every
written block (main loop and subagents alike) and stored with the session
entry. A `/resume` or a template change re-renders each block from its own
identity, so a block written under `M1` is never relabeled `M2` when the model
is switched later.
====

== Transcript colors

The transcript keeps one color per speaker: user turns are painted with the `yca.tui.primary` accent and assistant turns with `yca.tui.accent`, from the turn header and left bar down to the bold prose (unless `yca.tui.strongColor` pins an explicit bold color).
These settings are documented in the xref:../configuration.adoc[configuration] reference.
The markdown headings in assistant turns follow a fixed brand ladder: level 1 uses the accent color, level 2 the success (green) tone, level 3 the primary (purple) tone, and deeper levels keep the plain bold heading text; the heading tones are not configurable.
Palette colors default to `auto` and follow the active named theme (`dark` or `light`); an explicit hex overrides the theme for that slot.
The screen background defaults to `auto`, which keeps the terminal background untouched so a transparent terminal (e.g. Terminator) shows through; set `yca.tui.background` to a hex color to paint a translucent veil of that color over the terminal (see `yca.tui.backgroundOpacity`), or to an empty string to explicitly keep the terminal background.
The inline code color follows the selected code theme by default.
Markdown blockquotes use a continuous rail, and GitHub-style `[!NOTE]`, `[!TIP]`, `[!IMPORTANT]`, `[!WARNING]`, and `[!CAUTION]` callouts display a labeled rail.
Their colors can be overridden globally with `yca.tui.markdown.quote`, `note`, `tip`, `important`, `warning`, and `caution`, respectively; each accepts a hex color or `auto` (the default).
Automatic colors follow the active palette's muted text, info, success, primary, warning, and error colors, respectively, including explicit palette overrides.
`yca.tui.glyphs=ascii` uses an ASCII rail and spinner, and `NO_COLOR` suppresses callout colors.
The latest informational status or toast remains available after it disappears from the screen: press `Alt+I` to open its full text, scroll with the wheel or navigation keys, and press `c` to copy it.
Warnings and errors retain their separate `Alt+E` details, including the full message and any stack trace.
At startup, a nonblank `yca.tui.theme.name` takes precedence over the persisted `/theme` selection, which in turn takes precedence over the legacy `tui.theme` setting (default `dark`).
When `yca.tui.theme.name` is `auto`, the OS light/dark preference is detected at startup on a best-effort basis (macOS appearance, GNOME/KDE/GTK on Linux, Windows apps theme, `COLORFGBG` as a terminal fallback); when detection fails the normal precedence chain applies.
The `/theme light` and `/theme dark` commands still switch the current theme and persist the selection, but an explicit `yca.tui.theme.name` takes precedence again on the next startup.

Captured log regions (the inline log panels) never reuse a role color: each JUL
level keeps its own hue, configurable per level:

[source,json]
----
{
  "tui": {
    "log": {
      "severe": { "color": "#ff0000" },
      "warning": { "color": "#ffd700" },
      "info": { "color": "#00ffff" },
      "config": { "color": "auto" },
      "fine": { "color": "auto" },
      "finer": { "color": "auto" },
      "finest": { "color": "auto" }
    }
  }
}
----

`auto` (the default) follows the closest palette accent: `severe` uses the
error hue, `warning` the warning hue and the remaining levels the info hue
(dimmed for the debug levels), so the light theme palette keeps log regions
readable. Replace it with a hex color to pin a level tone.

Log regions render as plain text: there is no background tint, the level color
lives on the thin left bar and the bracketed `[LEVEL]` marker, and the logger
and timestamp groups stay muted. WARNING and SEVERE additionally render their
message bold so severe rows stand out from the INFO/debug noise.

== Side questions (/btw)

While a turn runs, `/btw <question>` asks a side question without interrupting
the running turn.
The question is an orphan by design: it is not added to the conversation, not
persisted to the session and not echoed to the transcript, so the next turns
never see it.
By default the answer is a single generation that never executes anything: it reuses
the session's system-prompt prefix and tool schema so the provider prompt cache
stays byte-identical with the main agent loop, and the model is directed to answer
directly and never act. A model that still reaches for a tool - natively or through
in-band text markup - is never executed and is surfaced as a retryable note rather
than a silent truncated answer.
With `yca.slashcommands.btw.tools` enabled the answer instead runs a bounded
read-only tool loop: the model can read files, search and run plan-mode commands
(the same global bash allow-list used in plan mode, so a refused command simply
means "not allowed"), and it is never granted write access or permissions-all mode.
Mutating commands trigger the approval gate like any other command in the
session, but the side loop stays bounded and keeps the turn running.
The last few side questions are replayed to the model so follow-up side
questions stay coherent.
In the xref:../cli/tui.adoc[`tui`] the answer opens a modal titled `btw`:
the mouse wheel or `Up`/`Down` scroll it, `Esc` closes it and cancels the
request if still running, and the main turn keeps streaming underneath.
In the xref:../cli/cli.adoc[`cli`] the answer is printed inline as a delimited
block once ready.

[opts=headers]
|===
|Property |Default |Description

|`yca.slashcommands.btw.model`
|provider model
|Model answering side questions when set, the session model otherwise.

|`yca.slashcommands.btw.maxTokens`
|0
|Maximum output tokens of an answer, 0 follows the provider/model budget.

|`yca.slashcommands.btw.maxHistoryMessages`
|200
|Most recent session messages inherited as context, 0 keeps everything.

|`yca.slashcommands.btw.recall`
|5
|Previous side questions replayed for follow-ups, 0 disables the replay.

|`yca.slashcommands.btw.tools`
|false
|When false (default) /btw is a one-shot that never executes; the session system prompt and tool schema are kept for the provider cache and stray tool attempts surface as a retryable note. When true, /btw may also run the plan-mode read-only tools.
|===

== Sessions on exit

When a session is left (`/exit`, `/quit`, `Ctrl+C` or a terminal close), its id
is logged so the user can find it again with `/resume <id>`.
In the `tui`, where several tabs can be open, each persisted session logs its
own line: `session <id> (<tab title>)`.
Sessions with a single prompt and no reply are discarded, so only sessions worth
resuming are reported.
