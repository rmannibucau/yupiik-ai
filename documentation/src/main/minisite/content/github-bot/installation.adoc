= Bare-metal Docker and Nono walkthrough

TIP: For a first single-server deployment, use the xref:simple-setup.adoc[simple, functional Linux/Docker setup] instead: it provides the complete phased path from artifact transfer through manual acceptance and scheduling.
This page covers broader Docker/Nono choices and image details.

WARNING: Strict Docker review/help/solve has live acceptance evidence, but Nono and additional isolation modes still need deployment-specific validation.
Start with a disposable test repository, not unattended production solving.
Docker socket access is equivalent to host administration; run the dispatcher on a dedicated trusted host.
For Nono, use a dedicated non-root OS account, not a human login with unrelated credentials.

== Prepare the dispatcher and Docker agent

Install JDK 25 and obtain the packaged bot fat JAR from your trusted build pipeline.
Docker is the primary executor.
For enforced egress, use trusted Linux Docker Engine 28 or later with bridge firewall isolation enabled, a dedicated non-root dispatcher with Docker control privileges, and a separately built trusted gateway image pinned by digest.
Rootless Docker, Docker Desktop, custom network plugins and disabled daemon firewall isolation are not verified enforcement targets.
Ordinary unit tests require no local Docker CLI or daemon; the opt-in live topology probe must pass on the deployment host before relying on network enforcement.
See xref:egress.adoc[Docker egress prerequisites, image build, allowlisting and validation] before enabling it.
From the repository root, with reactor dependencies already installed by your trusted build pipeline:

[source,bash]
----
mvn spotless:apply -pl extensions/github-bot -Pimage-agent compile jib:dockerBuild \
  -Dgithub-bot.agent.base-image=YOUR_REGISTRY/vetted-agent-toolchain@sha256:YOUR_BASE_DIGEST
export BOT_JAR="$PWD/extensions/github-bot/target/github-bot-1.0.0-SNAPSHOT-fatjar.jar"
java -jar "$BOT_JAR" --help
----

Expected outcome: the pipeline's executable dispatcher fat JAR and a separate local `yca-github-agent:local` image.
The agent base is mandatory and has no default: supply an operator-reviewed, credential-free toolchain image containing JDK 25, git, gh, a shell, CA certificates and all build tools required by your repositories (for example Maven, Node/npm and Python).
Jib layers the application onto that base; it does not install development tools, and a stock JRE base is not a usable agent toolchain.
Ensure `java` and the tools are on the base image's `PATH` and readable/executable by UID/GID 10001 without root initialization.
Verify the toolchain works with a read-only root filesystem, writable attempt directories and `/tmp`, and no ambient user credentials.
Pin both base images and deployed images by digest in production, not just by mutable tags.
The dispatcher runs on the host in this walkthrough, not in a socket-mounted container.
If selecting Nono instead, prepare the runtime described below and omit the Docker image build.

== Jib image profiles

All bot images use `com.google.cloud.tools:jib-maven-plugin:3.5.2` in `extensions/github-bot/pom.xml`.
Select exactly one image profile per invocation.
No image goals are bound to `test`, `package` or any other lifecycle phase; even with a profile selected, image creation requires an explicit `jib:dockerBuild`, `jib:build` or `jib:buildTar` goal.
The examples use module-only invocation after the pipeline has installed its reactor dependencies, avoiding image goals on unrelated modules.

[cols="1,2,2,2",options="header"]
|===
|Profile |Base property (default) |Target property (default) |Runtime
|`image-dispatcher` |`github-bot.dispatcher.base-image` (`eclipse-temurin:25-jre`) |`github-bot.dispatcher.image` (`yca-github-dispatcher:local`) |`CliLauncher`, UID/GID 10001, `HOME=/tmp`
|`image-agent` |`github-bot.agent.base-image` (required; no default) |`github-bot.agent.image` (`yca-github-agent:local`) |`CliLauncher`, UID/GID 10001, `HOME=/attempt/storage`
|`image-egress` |`github-bot.egress.base-image` (`eclipse-temurin:25-jre`) |`github-bot.egress.image` (`yca-egress:local`) |`EgressGateway`, UID/GID 65532, `-Xmx128m`
|===

The Kubernetes dispatcher uses the same `image-dispatcher` profile: Fusion's embedded client needs no external Kubernetes CLI.
Jib generates the Java entrypoint and runtime classpath from module classes and runtime dependencies, independently of the shaded fat JAR used for host execution.
No launcher script or fixed in-image JAR path is needed.
The agent has no baked-in command arguments: the executor appends `run` and its YCA arguments directly to the generated `CliLauncher` entrypoint.
Provision `/attempt/storage` as writable by the executor UID; setting `HOME` does not create or grant access to the mounted directory.

For a local dispatcher image, use:

[source,bash]
----
mvn spotless:apply -pl extensions/github-bot -Pimage-dispatcher compile jib:dockerBuild
----

`jib:dockerBuild` requires the local Docker CLI/daemon and loads the image there.
Use `jib:build` to publish directly to a registry without a Docker daemon, with registry authentication supplied through your trusted credential helper or Maven settings, never committed credentials.
Use `jib:buildTar` for an image archive at `extensions/github-bot/target/jib-image.tar` with the default build directory.
Override the appropriate base property with `REGISTRY/BASE@sha256:DIGEST` for each production build.
After publishing, record Jib's `target/jib-image.digest` for that module and configure the executor or deployment with `REGISTRY/IMAGE@sha256:DIGEST` rather than the build tag.
Keep these digests and the reviewed toolchain provenance with your deployment records.

== Create disjoint private state and attempts

Run these commands as the dedicated dispatcher account, using real directories without symbolic path components:

[source,bash]
----
umask 077
install -d -m 700 "$HOME/.local/state/yca-github" "$HOME/.local/share/yca-github-attempts"
export GITHUB_HOME="$HOME/.local/state/yca-github"
export GITHUB_EXECUTOR_ATTEMPTROOT="$HOME/.local/share/yca-github-attempts"
export GITHUB_REPOSITORIES_EXPLICIT="YOUR_OWNER/YOUR_TEST_REPOSITORY"
export GITHUB_AUTHORIZATION_USERIDS="YOUR_NUMERIC_GITHUB_USER_ID"
export GITHUB_LOGIN="YOUR_BOT_LOGIN"
export GITHUB_EXECUTOR_BACKEND=DOCKER
export GITHUB_EXECUTOR_DOCKER_EXECUTABLE=/usr/bin/docker
export GITHUB_EXECUTOR_DOCKER_IMAGE=yca-github-agent:local
----

Adapt trusted executable paths to your host.
The state directory is never exposed to an agent, and the attempts root must not be within it.
Use `gh api users/YOUR_LOGIN --jq .id` to find your immutable numeric ID.
An empty authorization list fails closed.
Use xref:configuration.adoc[the generated configuration and CLI references] for supported fields and defaults, not invented launcher options.

Provision a host token with metadata/issues/pull-request read access and final publication permissions appropriate to the tasks you enable.
Keep it in a secret manager or private environment file, never command-line arguments:

[source,bash]
----
read -r -s -p 'Host GitHub token: ' GH_TOKEN
export GH_TOKEN
java -jar "$BOT_JAR" github bot list
----

Expected outcome: `{"tasks":[]}` for a fresh queue.
The host token is not inherited by the executor.

== Smoke-test polling and publication

The default first scan starts at `now`; establish that watermark before posting the test comment:

[source,bash]
----
java -jar "$BOT_JAR" github bot poll
----

Then post `@YOUR_BOT_LOGIN help` in the test repository from the authorized account and run:

[source,bash]
----
java -jar "$BOT_JAR" github bot poll
java -jar "$BOT_JAR" github bot list
java -jar "$BOT_JAR" github bot poll
java -jar "$BOT_JAR" github bot worker
----

Expected outcome: the mention creates one task, the unchanged poll creates zero, and the worker publishes help once.
An unauthorized user's mention must not enqueue a task.
Inspect the stored `actorId`, reference and repository before enabling execution.
Help does not launch an agent and is not an isolation test.

=== Optional Discussions smoke test

Leave Discussion polling disabled until the disposable repository has Discussions enabled and the host credential has GraphQL Discussions read/write permissions.
Run `java -jar "$BOT_JAR" github bot poll --poll-pollDiscussions true` before posting a new test mention, or deliberately choose an initial backfill instant.
The equivalent poller environment setting is `POLL_POLLDISCUSSIONS=true`; this does not enable native-review polling.
Test authorized `help` mentions separately in a Discussion body, a top-level comment and a reply, then repeat polling and worker invocation to verify one task and one correctly threaded response per invocation.
Check that self, unauthorized-user and task-marked mentions enqueue nothing, and that Discussion `review` requests enqueue nothing because reviews are unsupported there.
Polling must not invoke an LLM or executor, and help must not launch one either.
Only then test a solve with a verified fork, confirming that the new PR is independently verified and linked back into the originating thread.
Do not substitute an issue comment or a matching marker from another thread as publication evidence.
Per-connection scan budgets do not bound the whole poll; retained Discussion/thread history increases API cost and needs operator capacity planning.
Live Discussion acceptance results for this changing implementation are pending and must be recorded separately from existing issue/review checks.

== Provision trusted agent configuration and credentials

Create `$GITHUB_HOME/agent-configuration.json` using provider fields from your working ordinary YCA JSON configuration.
Only `provider`, `model`, `llm`, `compaction`, `pruning` and `compression` are copied into attempts.
Memory, skills, MCP, notifications and subagents are force-disabled, hooks are cleared, permissions use YOLO inside the sandbox, and project-local configuration loading is disabled.
Do not copy the host token or unrelated integration settings into this file.
For example, adapt the provider details to your actual provider configuration:

[source,json]
----
{
  "provider": {
    "baseUrl": "https://YOUR_PROVIDER/v1",
    "apiKey": "PROVISION_USING_YOUR_SECRET_MANAGER",
    "model": "YOUR_MODEL"
  }
}
----

[source,bash]
----
chmod 600 "$GITHUB_HOME/agent-configuration.json"
export WORKER_FORKOWNER="YOUR_FORK_OWNER"
read -r -s -p 'Agent GitHub token: ' GH_AGENT_TOKEN
export GH_AGENT_TOKEN
read -r -s -p 'Fork write token (if required): ' GITHUB_BOT_FORK_TOKEN
export GITHUB_BOT_FORK_TOKEN
----

Pre-create a fork under the chosen owner and verify its upstream parent before solve testing.
Use a separate agent credential for upstream context, pull requests and reviews.
Provision a separate fork-write credential when resource-owner boundaries require it; a fine-grained PAT cannot assign different permission levels per selected repository.
The agent receives `GH_AGENT_TOKEN` as `GH_TOKEN`; the host token remains private.
Agent credentials and provider configuration can be misused despite prompt instructions; grant the smallest practical permissions.

== Select Nono instead of Docker

Nono execution requires Linux with supported supervised sessions and pathname AF_UNIX mediation.
Unsupported kernels or Nono versions must reject the profile; there is no unsandboxed fallback.
Install a trusted Nono executable outside agent-writable paths.
Prepare a dedicated credential-free runtime distribution, for example `/opt/yca-nono-runtime`, containing the agent launcher, JDK, libraries, git, gh, shell and all required build tools.
Provide required dynamic loader, runtime libraries, CA trust and other tool data within permitted runtime paths; host `/usr`, the human home and arbitrary system directories are not broadly granted by the generated profile.
Validate the distribution on the exact kernel and Nono version you intend to run.
Nono's filesystem/network sandbox and supervised sessions do not themselves enforce the executor's CPU, memory, process-count or storage limits.
Before enabling untrusted execution, apply external cgroup/service resource containment to the dedicated dispatcher service and all agent descendants, including CPU quotas, memory limits and process-count limits, plus filesystem quotas or equivalent bounded attempt storage.
Validate that child processes remain in that containment and cannot escape or exhaust the host; timeouts and bounded logs are not substitutes for resource limits.
The dispatcher account must be able to read and execute the runtime but must not let agent work modify it.
Do not put secrets, queue data, attempts, sockets or user configuration in the runtime tree.

`github.executor.nono.agentExecutable` is an executable launcher, not a JAR path.
For example, provision `/opt/yca-nono-runtime/bin/yca-agent` with mode 0555 and this content, adapting the runtime layout:

[source,sh]
----
#!/opt/yca-nono-runtime/bin/sh
exec /opt/yca-nono-runtime/jdk/bin/java -jar /opt/yca-nono-runtime/lib/github-bot.jar "$@"
----

Both the interpreter and Java must really be available at those paths without symlinks to forbidden locations.
The backend invokes the launcher directly with `run` and YCA CLI arguments; it does not prepend `java -jar`.
The generated `agentExecutable` setting names the launcher; it must not point directly at a JAR.

Keep state, attempts and runtime mutually disjoint, then select:

[source,bash]
----
export GITHUB_EXECUTOR_BACKEND=NONO
export GITHUB_EXECUTOR_NONO_EXECUTABLE=/usr/local/bin/nono
export GITHUB_EXECUTOR_NONO_RUNTIMEROOT=/opt/yca-nono-runtime
export GITHUB_EXECUTOR_NONO_AGENTEXECUTABLE=/opt/yca-nono-runtime/bin/yca-agent
----

`GITHUB_HOME` is also Nono's private state root and must already exist, be owned by the dedicated non-root account and have mode 0700.
Each runtime ID gets a private subdirectory containing launch intent, staged configuration, profile and supervised-session state.
Do not place that state under the runtime or attempts root and do not grant broad read access to it.
Only the staged configuration file is readable by the agent; the runtime is read-only and the current attempt's storage/workspace/output are writable.
The subprocess environment is rebuilt, with `PATH` restricted to the runtime's `bin` directory plus the explicitly forwarded agent credentials and attempt-local home/temp settings.
Provision every tool needed by the launcher accordingly; ambient `JAVA_HOME`, developer shell configuration and credentials are not inherited.

== Verify real execution and schedule

Post a small solve or review mention in the disposable repository, then run:

[source,bash]
----
java -jar "$BOT_JAR" github bot poll
java -jar "$BOT_JAR" github bot list
java -jar "$BOT_JAR" github bot worker --task TASK_ID
java -jar "$BOT_JAR" github bot show --task TASK_ID
----

Replace `TASK_ID` with the queued ID.
The worker claims at most one task per invocation and requires a bounded structured `output/result.json`; a URL in a console log is not success.
In the default credentialed workflow the repository is not pre-cloned; the executor fetches context with `gh` using the separately provisioned credential, unless the optional public clone cache is enabled.
Strict mode instead stages credential-free host context and source, including private source for strict solve; see xref:private-context.adoc[private context and host publication] for permissions, bounds and unsupported cases.
Verify the resulting fork/branch pull request and its originating issue/Discussion response, or the head-pinned native review itself, not only the process exit code.
Successful reviews deliberately publish no additional acknowledgement comment.
The core result-file guard can request one same-session repair continuation, but the host still enforces task identity, narrower non-solve size limits and independent publication validation.
Inspect the selected backend while running to confirm it has no queue access, host credential or host administration socket.
Completed and superseded attempt directories are cleaned; logs are bounded to 8 MiB and are not a permanent diagnostic archive.
Nono private state is removed with task cleanup only after its registry proves termination; ambiguous sessions remain for operator recovery.
The xref:configuration.adoc[cleanup command] safely removes old unreferenced prepared-only attempts, never launchable orphan evidence.

Schedule separate private wrappers that load secrets and invoke `poll` or `worker` once with the same configuration.
For example, after provisioning those wrappers:

[source,text]
----
* * * * * /usr/local/bin/yca-github-poll
* * * * * /usr/local/bin/yca-github-worker
----

The application serializes pollers with `poll.lock`, workers with `worker.lock`, and state writes with a separate sidecar lock.
A slow worker does not need to block polling, and a later worker invocation may find no work.
Do not enable schedules until successful execution and crash recovery have been exercised on the chosen runtime.

== Recover safely

Disable both schedules and stop new launches before maintenance.
Inspect the task and audit identifiers with `show`; keep state and secret-bearing attempts private and preserve evidence if runtime termination is uncertain.
For a task left `running`, invoke the same backend worker for that task after repairing runtime access; it uses the persisted runtime identity to stop and confirm termination before reading a result or permitting further work.
For Nono, a missing or ambiguous session registry, missing supervisor, or negative reconciled exit code is not proof that children stopped.
Do not delete Nono intent/session state or substitute a raw PID kill to bypass recovery; establish termination using the supervised-session identity, and fence the dedicated host if necessary.
Do not change backend or attempt-root paths while recoverable tasks remain.
Reconcile ambiguous GitHub publications and existing task-branch pull requests before considering retries.
Use `github bot retry --task TASK_ID` only for an unpublished failed task with no retained attempt data after checking side effects and runtime identity.
Already-published failures cannot be reset: create a new manual task for a new request instead.
Retry does not reset the attempt counter, and runtime IDs are single-use.
Use `purge` for clean terminal task retention, not as an orphan-process cleanup mechanism.
See xref:security.adoc[security and recovery] for remaining limitations.
Existing disposable-repository evidence covers Docker strict review and a separate native-review acknowledgement-loss fixture, not Nono, Kubernetes, strict solve or live Discussion acceptance.
The acknowledgement-loss fixture proves reconciliation after GitHub accepted a review before its response arrived; it does not establish execution-time crash safety or blanket production readiness.
No new live workflow or build was executed by these documentation changes.
