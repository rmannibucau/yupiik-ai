= GitHub bot
:minisite-index: 650
:minisite-index-title: GitHub bot
:minisite-index-description: Polling, durable tasks and isolated headless execution.

The experimental `extensions/github-bot` module is a JVM-only GitHub polling application built on YCA core, without the terminal UI dependencies.
It has no inbound webhook endpoint.

WARNING: This is an initial implementation, not the complete production architecture.
The CLI supports repository discovery and filters, PAT/App host authentication, immutable user-ID authorization, polling and durable task operations.
Docker, Nono and Kubernetes execution are integrated through the worker, with strict host publication or separately provisioned agent credentials, and verified task-branch pull requests or native head-pinned reviews before reporting success.
The strict Docker review/help/solve path has live acceptance evidence; that does not establish every backend's isolation or blanket production readiness.
Do not deploy unattended production solving before validating permissions and recovery in a disposable repository.

== Current contracts

An empty authorization list denies all polling.
Authorization uses immutable numeric GitHub user IDs, not mutable login names.
Issue bodies, issue comments and review comments are scanned independently.
Task-marked bot output is never parsed as an invocation, including native review summaries and inline findings, even when the publishing account differs from the configured mention login.
Help examples use inline code so copying the example text alone does not invoke the bot.
Successful reviews finish with the native review itself; no additional comment announces that a review was published.
Solve responses link the verified new pull request back to the originating issue or enabled Discussion thread.
Discussion polling is opt-in with `poll.discussions.enabled=false` by default; bodies, top-level comments and replies support `help` and `solve`, not `review`.
Discussion access uses GraphQL and requires host Discussions read permission for polling and write permission for responses.
Invocation receipts survive task deletion, so overlapping scans do not recreate deleted tasks.
A scan hitting its page budget does not advance its completed watermark.
State updates use short sidecar-lock transactions and atomic replacement; agent execution never holds the store lock.
Structured result files are required; a URL appearing in a transcript is not accepted as proof of success.
Ambiguous publication remains pending reconciliation rather than triggering model re-execution.

The default `maxRetries=2` means an initial execution plus two retries, not two attempts total.
CLI commands are finite one-shot operations; scheduling is external.

== Validation status and version 0 limits

A disposable private-repository Docker run has demonstrated strict private review publication, Discussions help routing for bodies/comments/replies, and strict solve-to-PR through a verified separately owned fork.
The published solve sources were independently fetched, compiled and tested; repeated polling and completed-task execution created no duplicate PR or response.
A separate live acknowledgement-loss check on 2026-11-12 killed the worker after GitHub accepted a native review and before the response reached the worker; restart reconciled one review without another comment or model execution.
That check covers publication acknowledgement loss only, not an execution-time crash or every remote mutation window.
This evidence covers the strict host-published workflow, not the separate credentialed-agent git/gh workflow, Nono, Kubernetes or enforced egress.
The recorded bot-module suite passed 229 tests with no failures or errors and three skips; a prior broader core suite had exploration-plateau failures, so no blanket green whole-reactor claim is made.
Version 0 still requires external scheduling, operator-managed retained state and fail-closed operator reconciliation for uncertain writes.
See xref:security.adoc[security and recovery] and xref:configuration.adoc[Discussion scan and completion contracts] before enabling additional workflows.
